## 2. 上手路线（按“最小可跑闭环”到“面试级闭环”）

### 2.1A 面试级闭环（1-2 周，做出“可解释的提升”）

这一阶段不要再满足于“脚本跑通”，目标是做出一条能自洽的证据链：
- 数据侧：证明你做了 **目标分布对齐**，而不是随机抽医疗数据。
- 训练侧：证明你做了 **至少 1 次有效消融**，而不是只报一组最优结果。
- 评测侧：证明你看的不是单一指标，而是 **CEval + 主观样例 + 资源成本** 的组合。

建议把这部分拆成 `数据构造 -> SFT 基线 -> SFT(召回筛选) -> DPO/PPO -> CEval 对比 -> 消融总结` 六步。

#### A. 数据：做“目标分布对齐”的筛选或构造

核心目标：让训练数据分布更接近目标评测任务，减少 random sampling 带来的 domain mismatch。

可直接落地的最小方案：
1. 选锚点任务：先用你已经跑过的 `ceval-valid_basic_medicine` 和 `ceval-valid_clinical_medicine` 作为目标分布锚点。
2. 构造锚点文本：把每道题拼成统一文本，例如 `题干 + 选项A/B/C/D`，不要带正确答案。
3. 选候选 SFT 数据池：优先从 `shibing624/medical` 的问答类数据或你后续整理的医疗 SFT 数据中抽一个可控规模子集，例如 `5k~50k`，不要一上来全量 200w。
4. 做 embedding：分别对锚点题目和候选 SFT 样本的 `instruction/question` 侧做向量化。
5. 计算相似度：对每条候选样本，计算它与锚点集合的 `max cosine similarity` 或 `top-k mean similarity`。
6. 设阈值筛选：先试 `0.70 / 0.75 / 0.80` 三档，不要一开始拍脑袋定死。
7. 去重：对召回结果做文本级去重和近重复去重，防止高相似样本成簇出现。
8. 落盘：生成 `train_random.jsonl`、`train_retrieved_t70.jsonl`、`train_retrieved_t75.jsonl` 这类可追溯文件。

推荐的工程实现：
- Embedding 模型：优先 `BAAI/bge-large-zh-v1.5`；如果显存或速度受限，可退到 `BAAI/bge-small-zh-v1.5`。
- 相似度定义：优先 `cosine similarity`。
- 样本表示：优先只对 `human/instruction/question` 这一侧做 embedding，不要把 `gpt/answer` 拼进去；否则容易把回答风格噪声引进召回。
- 最近邻策略：优先 `max similarity to anchor set`，因为实现简单、可解释；后续再尝试 `top-3 mean`。

为什么先推荐 `bge-large-zh-v1.5`：
- 中文检索能力强，语义匹配稳定。
- 医疗任务里很多是“症状/疾病/处理建议”语义近邻，embedding 质量比生成模型的直觉判断更稳定。
- 面试时也好解释：你不是凭主观规则筛数据，而是用统一语义空间来做分布对齐。

阈值怎么定：
- 不要直接回答“我用 0.75”，要回答“我先做阈值扫描”。
- 最少做 3 档：`0.70 / 0.75 / 0.80`。
- 每档记录 4 个数：`召回样本数`、`平均相似度`、`去重后样本数`、`CEval acc`。
- 面试里的正确说法是：阈值越低，数量越大但噪声更多；阈值越高，质量更纯但覆盖不足。我用这组实验画了一个“数据量-质量-指标”的帕累托关系，而不是只报一个点。

去重怎么做：
- 第 1 层：精确去重。对 `human + gpt` 或 `question + answer` 做规范化后 hash 去重。
- 第 2 层：近重复去重。对 `human/question` 做 embedding，相似度超过 `0.95` 的保留一条；或者用 MinHash/SimHash 做近重复过滤。
- 第 3 层：来源配额控制。如果你混了多源医疗数据，限制单一来源占比，例如不超过 `20%~30%`，避免一个来源主导分布。

如何证明没有 test 泄露：
- 只拿 `dev/valid` 做锚点，不碰 `test`。
- 锚点文本不包含标准答案，只包含 `题干 + 选项`。
- 召回后的训练集与 CEval 题干做字符串去重和近似去重；命中就剔除。
- 评测时保留单独 held-out 集，或者至少保留你没用作锚点的任务作为旁证。
- 面试话术要明确：这是 **distribution alignment**，不是把 test 答案喂给模型。

#### G. 把候选池扩到 5k+ 的实际做法

当前仓库里没有落地的 `HealthAI` 原始病例文件，也没有 `shibing624/medical` 的大规模 SFT 文件，所以这一步的关键不是调阈值，而是先把外部数据接入仓库。

你给出的 `shibing624/medical` 链接和目录信息，已经足够把“数据构造”这部分落成一个明确流程。核心判断如下：
- `finetune/train_zh_0.json`：这是第一优先级，约 `195万` 条中文医疗问答，是构建 `5k+` SFT 候选池的主力来源。
- `finetune/train_en_1.json`：约 `11万` 条英文医疗对话。如果你的 base model 主打中文医疗面试，第一轮可以先不混；如果后面想讲中英双语泛化，再单独做扩展实验。
- `reward/train.json`：约 `3800` 条偏好对，用于 RM / DPO，不直接并入 SFT 候选池。
- `pretrain/train_encyclopedia.json`、`medical_book_zh.json`：这是 PT 数据，不适合直接拿来做问答式 SFT 检索候选池。它们适合后面讲“增量预训练注入医学知识”，不适合混进当前这条 `Random SFT vs Retrieved SFT` 消融。

也就是说，第一版候选池最干净的做法是：
- 主源：`medical/finetune/train_zh_0.json`
- 辅源：你自己的 `HealthAI-2025` 病例转 SFT 数据
- 暂不引入：`train_en_1.json`、`reward/train.json`、`pretrain/*.json`

为什么这么选：
- 你的评测锚点是中文 CEval 医学题，先用中文问答数据做候选池，分布更一致。
- `train_zh_0.json` 本身就是 `instruction/input/output` 结构，天然适合转成 MedicalGPT 的 `conversations` 格式。
- `reward/train.json` 的任务定义是偏好排序，不是直接 supervised answer generation；混入 SFT 会污染任务边界。
- `pretrain` 语料是长文本，不是指令跟随数据；它更适合 PT，不适合现在这条面试级 SFT 消融。

#### G4. 面试里“数据构造”这段该怎么讲

这部分建议你按这个逻辑讲：
- 我先把 `shibing624/medical` 按任务类型拆开看，不是把 240 万条数据一股脑混进来。

- `reward/train.json` 留给 RM / DPO，`pretrain/*.json` 留给 PT，不混任务边界。
- 如果有 `HealthAI` 病例数据，就把它转换成 `主诉/现病史/检查检验 -> 诊断/处置建议` 的 SFT 样本，再和 `medical` 问答数据混合。
- 然后再做 CEval 锚点召回，而不是直接在全量数据上随机采样。

这样讲的好处是：
- 你体现了自己理解“数据来源很多，但不能乱混”。
- 你体现了自己理解 `PT / SFT / RM` 三类数据的任务边界。
- 你后面做消融时，结论会更可信。

- 第一优先级：`shibing624/medical` 的 SFT 问答数据。这个最适合直接扩成 `5k~20k` 候选池。

- 第一版候选池先做成 `70%` 通用医疗问答 + `30%` 结构化病例转 SFT。

RM 这一步在做什么（面试要讲清楚）：
- 目标：训练一个“打分模型”，让它学会对同一个问题下的两个回答打分，并满足 `score(chosen) > score(rejected)`。
- 输入形式：不是直接拿 `question` 单独训练，而是把 `question + response_chosen` 和 `question + response_rejected` 分别按同一个 `template_name` 拼成两条完整 prompt，再分别送进模型。
- 模型形式：`reward_modeling.py` 用的是 `AutoModelForSequenceClassification(num_labels=1)`，也就是把大语言模型改成“每条输入输出一个标量分数”的序列分类头，而不是生成下一个 token。
- 损失函数：仓库里实现的是 pairwise log loss，核心形式是 `-log(sigmoid(reward_chosen - reward_rejected))`。直觉上就是“让 chosen 的分数比 rejected 更高，而且差距越稳定越好”。
- 为什么做 RM：后面如果走 PPO，RM 就是奖励函数；即使你最后主线走 DPO，RM 这一步也能证明你理解 RLHF 的完整链路，而不是只会跑偏好优化。
- 为什么这一步重要：SFT 解决的是“像不像一个会回答问题的助手”，RM 解决的是“哪个回答更符合偏好、更安全、更贴近你定义的质量标准”。

RM 的工程注意点（这部分很容易被问）：
- `template_name` 必须和前面 SFT/后面推理保持一致。你当前链路用的是 `qwen`，RM 也必须继续用 `qwen`，否则 chosen/rejected 的 prompt 格式会漂移。
- `train_file_dir` 和 `validation_file_dir` 如果都指向 `data/reward/`，本地阶段更像“流程验证 + 指标监控”，不是严格 held-out 评测。真正做面试级结果时，建议显式切分一个 unseen validation/test。
- RM 的显存占用和 SFT 不完全一样。虽然基座模型还是同一个，但每个样本要同时处理 chosen/rejected 两条序列，所以长度和 batch size 对显存影响更敏感。
- 对你现在的 `1 x 48GB 4090` 来说，`Qwen2.5-0.5B + bf16 + LoRA + per_device_batch_size=4 + grad_acc=8` 是比较稳妥的起点；先把全量 `500` 对偏好数据跑通，再决定要不要增大 batch 或换更大的 base model。

为什么 RM 先用这套配置（面试时建议按这个逻辑讲）：
- `Qwen/Qwen2.5-0.5B-Instruct`：先用小基座把 RM 链路跑通，优先验证数据格式、模板、损失函数和输出目录，而不是一上来追大模型效果。RM 阶段的重点是“偏好打分逻辑是否成立”，不是参数规模本身。
- `LoRA`：RM 只需要让模型学会偏好排序，不一定要全参更新。LoRA 可以显著减少可训练参数和显存占用，让单卡实验更稳定，也更符合你当前“先做可复现基线”的目标。
- `bf16`：bfloat16 训练比 float32 更省显存和带宽，同时比 fp16 更稳，动态范围更大，不容易因为数值范围太窄出现溢出/下溢。对 Ada 架构的 4090 来说，`bf16 + torch_dtype=bfloat16` 是一个比较自然的选择。
- `gradient checkpointing=True`：它会在前向传播时少存一部分中间激活，反向传播时再重算，从而显著降低显存占用。代价是训练速度会慢一些，但对 RM 这种“单卡先求稳”的阶段是值得的。
- `per_device_train_batch_size=4`：RM 每个样本实际上要同时处理 `chosen` 和 `rejected` 两条序列，所以显存压力比普通单路输入更大。把单卡 batch 先设为 4，是为了在 48GB 显存上留足余量，减少一开始就 OOM 的概率。
- `gradient_accumulation_steps=8`：单步 batch 设得保守后，用梯度累积把等效 batch 放大到 `4 x 8 = 32`。这样既保住了显存安全边界，又能让梯度统计更稳定，不至于因为 batch 太小导致波动过大。
- `train=500 / eval=50`：本地阶段先用仓库自带的 500 条偏好对做一个“可闭环基线”，再抽 50 条做 eval 监控。这样可以快速验证 RM 的 loss、MSE、MAE 是否正常输出，先解决“能不能稳定训练”的问题，再谈严格评测切分。
- `max_source_length=1024`：source 侧对应的是问题、system prompt、history 等上下文。先给到 1024，是为了覆盖大多数样本的上下文，同时控制显存和 padding 开销。
- `max_target_length=256`：target 侧对应 chosen/rejected 回答的主体长度。先设 256 是一个工程折中：既能覆盖大部分偏好回答，又不会因为长尾超长回答把 RM 的单样本成本抬得太高。
- `template_name=qwen`：RM 不是直接比较裸文本，而是把 `question + answer` 按模板拼成完整 prompt 后再送入模型。如果模板和 SFT/推理阶段不一致，模型看到的输入分布会变，偏好学习会失真，所以这里必须和前面保持一致。

把这套配置翻成一句面试话术，可以这样说：
- 我在 RM 阶段先用 `Qwen2.5-0.5B + LoRA + bf16 + gradient checkpointing` 做单卡基线，核心思路是先把偏好学习链路稳定跑通，再逐步放大模型或样本规模；`batch_size=4 + grad_acc=8` 是在 48GB 显存上兼顾稳定性和有效 batch 的折中，`1024/256` 的长度设置则是在覆盖样本信息和控制显存成本之间做平衡。

这些参数如果被继续追问，你可以这样回答：
- 为什么不是全参：RM 首先是验证偏好排序能力，LoRA 足够支撑基线实验，而且更节省资源。
- 为什么不是 fp16：4090 支持 bf16，bf16 的数值稳定性通常比 fp16 更好，尤其是在长序列和梯度波动较大的训练里更省心。
- 为什么要 gradient checkpointing：因为 RM 每条样本要走 chosen/rejected 两次前向，激活开销比普通单路输入更敏感，用 checkpointing 换速度保显存是合理取舍。
- 为什么长度不是更大：RM 的目标不是生成长答案，而是比较两条回答的相对优劣；长度过大会明显抬高显存和训练时长，smoke/baseline 阶段没必要。

DPO 这一步在做什么（面试要讲清楚）：
- 目标：让模型直接学习“在同一个 prompt 下，更偏向 chosen、远离 rejected”。

### 2.2A `SFT -> RM -> DPO -> GRPO` 项目对比方案（建议直接按这个表推进）

这一版的核心目标不是把四条线都跑成“最好结果”，而是把它们放到同一套项目设计里，做到：
- 数据来源可解释
- reward 定义可解释
- 评测口径统一
- 最终结论能回答“为什么 DPO 先做、GRPO 为什么是后续增强路线”

#### A. 四阶段角色分工

| 阶段 | 训练目标 | 当前最适合的数据格式 | 是否能直接复用“分布对齐筛题” | 当前仓库状态 | 建议定位 |
|---|---|---|---|---|---|
| SFT | 学会医疗问答与指令跟随 | `conversations`（human/gpt） | 可以，直接复用 | 已跑通 | 主基线 |
| RM | 学会“哪个回答更好” | `question + response_chosen + response_rejected` | 间接可复用：先筛问题，再构造偏好对 | 已跑通 | 偏好打分器 / 为 PPO/GRPO 做准备 |
| DPO | 直接在偏好对上做行为对齐 | `prompt + chosen + rejected` | 可以，优先复用 SFT 的筛题逻辑 | 已跑通 | 当前主线对齐方法 |
| GRPO | 用生成采样 + reward 做策略优化 | `question + reference_answer/reward context` | 可以复用“筛题”，但不能直接复用 DPO 偏好对格式 | 代码存在，但当前 reward 设计偏数学题模板 | 后续增强路线 |

#### B. 数据设计：四阶段如何共用一条“分布对齐”主线

核心原则：统一在 `question / instruction` 这一侧做分布对齐，再按训练目标把样本转换成不同格式，而不是每个阶段各做一套数据工程。

建议统一从这三层数据池出发：
1. `Anchor Pool`：`ceval-valid_basic_medicine + ceval-valid_clinical_medicine`
2. `Candidate Pool`：`shibing624/medical/finetune/train_zh_0.json` + 可选 `HealthAI` 病例转 SFT
3. `Preference / Reward Pool`：`data/reward/dpo_zh_500.jsonl` 或后续扩展偏好对

建议的数据映射表：

| 阶段 | 输入样本怎么来 | 训练文件建议 | 备注 |
|---|---|---|---|
| SFT | 先做锚点召回，得到 `random / retrieved_t70 / retrieved_t75` | `data/finetune_ablation/*/train.jsonl` | 已有脚本可直接复用 |
| RM | 对筛中的医疗问题补 `chosen/rejected`，或从偏好集里筛出更贴近 CEval 分布的问题 | 新建 `data/reward_ablation/*.jsonl` | 优先保证字段与 `dpo_zh_500` 一致 |
| DPO | 直接使用 RM 同源偏好对 | `data/reward_ablation/*.jsonl` | 与 RM 共用问题分布最合理 |
| GRPO | 对筛中的问题保留 `question`，并补 `reference_answer` 或 reward 所需元信息 | 新建 `data/grpo_ablation/*.jsonl` | 不能直接拿 DPO 的 `chosen/rejected` 原样训练 |

#### C. Reward 设计：RM / DPO / GRPO 的关键差异

GRPO 这一步要特别注意：当前仓库 `grpo_training.py` 里默认的 `accuracy_reward + format_reward` 更像数学/可验证答案任务模板，不适合直接拿来做医疗开放问答。

建议把 reward 设计拆成下表：

| 方法 | reward 来源 | 当前是否已具备 | 医疗任务适配建议 |
|---|---|---|---|
| RM | Bradley--Terry pairwise loss 学到的标量分数 | 已具备 | 继续作为 learned reward 候选 |
| DPO | 不显式训练在线 reward，直接比较 `chosen/rejected` 相对概率 | 已具备 | 作为当前主线最稳 |
| GRPO-规则版 | 格式奖励、重复率惩罚、长度约束、安全兜底 | 部分具备，需要重写 | 适合先做 smoke / 工程验证 |
| GRPO-RM版 | 直接调用已训练 RM 给生成答案打分 | 方案上最合理，当前仓库未直接接好 | 最值得做的医疗版 GRPO 路线 |
| GRPO-混合版 | `RM reward + 格式 reward + 安全 reward` | 需实现 | 最适合后续做效果增强 |

如果真的推进医疗版 GRPO，建议 reward 先做成：
- `reward_total = 0.6 * rm_score + 0.2 * format_score + 0.2 * safety_score`
- 其中 `format_score` 检查结构完整性和明显重复
- `safety_score` 检查是否包含危险建议、是否提供必要就医提示

#### D. 统一评测表：四条线怎么公平比较

最终比较不要只看训练期 loss。建议统一落成下面这张表：

| 模型版本 | 数据版本 | 训练方式 | 统一 CEval | 主观样例 | 偏好胜率/人工胜率 | 资源成本 | 关键结论 |
|---|---|---|---|---|---|---|---|
| SFT-random | `random/train.jsonl` | SFT | `basic/clinical acc` | 10 条问答样例 | 可选 | 显存/时长 | 随机基线 |
| SFT-retrieved | `retrieved_t70/train.jsonl` | SFT | `basic/clinical acc` | 10 条问答样例 | 可选 | 显存/时长 | 验证分布对齐是否有效 |
| RM | `reward_ablation/*.jsonl` | RM | `eval_loss/mse/mae` + 可选 CEval 旁证 | 不作为主观生成模型单独比较 | 不适用 | 显存/时长 | 验证偏好打分链路 |
| DPO | 与 RM 同源偏好对 | DPO | `basic/clinical acc` | 10 条问答样例 | SFT vs DPO | 显存/时长 | 看行为对齐是否改善生成质量 |
| GRPO | `grpo_ablation/*.jsonl` | GRPO | `basic/clinical acc` | 10 条问答样例 | DPO vs GRPO | 显存/时长 + reward 曲线 | 看 reward 驱动优化是否进一步带来收益 |

建议最低保留这些评测输出：
- `CEval`: `basic_medicine / clinical_medicine` 的 `acc / acc_norm`
- `开放问答`: 至少 10 条固定 prompt 的对比输出
- `资源`: 峰值显存、训练时长、是否需要多卡
- `GRPO 特有`: reward 均值、格式合格率、各 reward 分项均值

#### E. 对比实验的推荐顺序

按你当前项目状态，最稳的推进顺序是：
1. `SFT-random` vs `SFT-retrieved_t70`：已经完成，可继续作为数据构造证据
2. `SFT-retrieved` vs `DPO`：已经完成，可证明偏好对齐改善生成稳定性
3. `DPO` vs `GRPO-规则版`：先验证 GRPO 能否稳定训练医疗问答
4. `DPO` vs `GRPO-RM版`：如果规则版可跑，再做更像项目亮点的对比

不建议一上来直接做：
- `SFT -> GRPO` 跳过 RM/DPO 的复杂大实验
- 直接把当前 `grpo_training.py` 原封不动用于医疗开放问答

#### F. 面试话术：怎么解释“为什么 DPO 先做，GRPO 后做”

建议直接这样讲：
> 我把 DPO 作为当前主线，是因为它对单卡资源更友好、训练更稳定，而且我已经有偏好对数据；GRPO 更像后续增强路线，它依赖 reward 设计是否合理。对于医疗开放问答，当前仓库自带的 GRPO reward 偏向可验证答案任务，所以我会先复用 DPO 那套分布对齐筛题思路，再把 RM 接成 learned reward，最后再比较 DPO 和 GRPO 的收益差异。

### 4.2 模型尺寸与微调数据量：为什么“更大模型 + 更多数据”也可能更差

这个问题现在已经有两个很好的真实例子可以讲：
- 你的 `0.5B` 随机 `500` 条 SFT，在统一 CEval 下没有带来提升；
- 你朋友的 `Qwen2.5-3B` 随机 `9000` 条微调，结果反而更差。

这两个现象放在一起，最重要的结论不是“模型越大越没用”，而是：**微调效果的关键变量不是模型大小或数据条数本身，而是模型容量、数据质量、数据分布、训练目标和评测目标之间是否匹配。**

常见原因可以归纳成 6 类：
1. **数据分布与评测目标不一致**：如果训练数据更像问诊闲聊、医疗百科或模板化建议，而评测看的是 CEval 这类医学知识选择题或临床判断题，就会出现“回答更像医生了，但 benchmark 反而下降”的现象。
2. **数据质量不均，噪声被放大**：数据量一大，重复样本、错误知识、低质量回答、风格噪声都会混进来；模型越能学习，越可能把这些偏差系统性学进去。
3. **大一点的模型不等于对脏数据更鲁棒**：`3B` 虽然比 `0.5B` 强，但还远不到可以无脑吞大量噪声数据的程度；如果数据不干净，它会更充分地学到这些偏差。
4. **超参与模型规模不匹配**：模型放大后，同样的学习率、batch size、训练步数未必还合适，可能导致过拟合、更新过猛或泛化变差。
5. **灾难性遗忘 / 能力挤压**：如果长期在单一风格医疗数据上训练，模型可能更会“说医疗话术”，但原有的通用推理或选择题判断能力反而被挤压。
6. **评测样本有限，波动会被放大**：像 CEval 医疗子任务题量不大，所以真实退化和 benchmark 方差经常会叠加出现。

更实用的经验不是“多少参数配多少条数据”，而是下面这个关系：

| 模型规模 | 对数据量的耐受度 | 对数据质量的敏感度 | 更适合的策略 |
|---|---|---|---|
| `0.5B` | 低到中 | 很高 | 少量高质量、强筛选、强分布对齐 |
| `3B` | 中 | 高 | 中等规模数据，先筛选再扩量 |
| `7B+` | 中到高 | 仍然高 | 可以扩更多数据，但仍要严格控分布和噪声 |

面试里最稳的说法是：
> 小模型不是不能吃大数据，但它的参数容量有限，所以收益不会随着数据量线性增长；相比盲目上全量，我更倾向于先做数据分布对齐和质量筛选，让有限参数优先学习对目标任务最有用的那部分信息。你现在的 `Random SFT(500)` 下降，以及朋友的 `3B + 9000` 下降，反而共同说明了“随机堆数据”不是一个可靠策略。

**总的项目结论：**
- 当前最可靠的 benchmark 正向收益来自“数据分布对齐”，而不是单纯上 DPO/PPO。
- DPO 当前更像“改善部分主观生成质量”的方法；PPO 当前更像“RLHF 主线已可落地”的工程验证。
- 对这类医疗项目，训练目标、偏好目标和评测目标并不天然一致，必须同时看 CEval、主观样例和训练日志，不能只看单一 loss 或 reward。

证据清单（每次跑完都要能指到文件）：
- 输出目录（含 `trainer_state.json`、`training_args.bin`、`eval_results.txt`、`logs/`）
- 评测命令与输出（原始 stdout/stderr 或保存到文本）
- 数据版本（jsonl 的 commit hash/文件 checksum/筛选阈值）

## 4.3 医疗 reward 数据替换方案（RM / DPO）

> **推荐的最终 DPO 对比组：**
> 当前真实进展：

>
> 三组 DPO 统一 CEval 结果：
> - old500：`basic=0.4737`，`clinical=0.5000`
> - medical500：`basic=0.4737`，`clinical=0.4091`
> - medical3800：`basic=0.5789`，`clinical=0.5000`
>
> 这说明医疗化偏好数据不是“换了就一定更好”。当前结果更像是：500 条医疗 reward 太少，反而不如旧 500；扩到 3800 后才恢复到 SFT baseline 水平，但仍没有超过“分布对齐 SFT”在 `clinical_medicine` 上体现出的最强收益。

三组 DPO 的固定 10 条医疗 prompt 主观对比也已经补齐，结论和 CEval 基本一致：
- `old500`：可读性相对最稳，虽然医学细节不够准，但回答通常更短、更完整；
- `medical500`：过长、重复、循环最明显，多个题目出现概念堆砌和局部崩坏；
- `medical3800`：比 `medical500` 稳定，说明扩量确实在修复退化，但主观样例里仍有模板化、重复和解释不够精准的问题。

这背后可能有 4 个主要原因：
1. **偏好数据的目标与 CEval/固定问答目标并不完全一致**：DPO 学到的是‘更像 chosen 的回答风格’，不一定等价于‘更准确地答医学题’。
2. **500 条医疗偏好数据覆盖不足**：虽然更医疗化，但题型、表达方式和错误模式覆盖不够，容易把模型带到局部风格而不是稳定泛化。
3. **扩到 3800 的收益更像“修复退化”而不是“新增能力”**：说明量的确重要，但更多是在缓解小样本偏差，并没有自然变成更强 benchmark。
4. **LoRA 容量本身可能也在限制偏好迁移**：当前 DPO/RM 统一用的是 `r=8`，它的优点是稳、省显存、省时间；但如果偏好模式更复杂，`r=8` 可能表达能力不够，只能学到比较粗的风格偏移。

关于 `r=8` 和 `r=16`，当前最稳的工程判断是：
- `r=8`：更省显存、更稳，适合先把闭环和控制变量实验跑通；
- `r=16`：参数容量更大，理论上能表达更复杂的领域偏移和偏好模式，可能让医疗 reward 数据学得更充分；
- 但 `r=16` 不会自动更好，它也可能更容易放大噪声、增加训练不稳定和过拟合风险。

最新统一 CEval 结果也支持这个判断：
- `medical500`：`r=8` 为 `0.4737 / 0.4091`，`r=16` 为 `0.5263 / 0.3636`，说明 `r=16` 虽然在 `basic_medicine` 上略有回升，但在更关键的 `clinical_medicine` 上进一步下降；
- `medical3800`：`r=8` 为 `0.5789 / 0.5000`，`r=16` 为 `0.4737 / 0.4091`，说明更高 rank 在扩量组上反而明显更差。

所以当前更合理的解释不是“rank 不够大”，而是：医疗偏好数据的质量、覆盖和分布仍然是主导变量，而 `r=16` 只是在更充分地放大这些偏差。

1. `medical500, r=8` vs `medical500, r=16`

## DPO LoRA Rank 消融：为什么 `r=16` 反而更差

这轮消融我把同一套医疗偏好数据分别用 `LoRA r=8` 和 `r=16` 跑了一遍，并同时看了统一 CEval 和固定 10 条医疗 prompt 的主观输出，结论很一致：**当前这条 DPO 线里，`r=8` 明显比 `r=16` 更稳。**

统一 CEval 结果：

| 组别 | basic_medicine | clinical_medicine |
|---|---:|---:|
| `medical500, r=8` | `0.4737` | `0.4091` |
| `medical500, r=16` | `0.5263` | `0.3636` |
| `medical3800, r=8` | `0.5789` | `0.5000` |
| `medical3800, r=16` | `0.4737` | `0.4091` |

固定 10 条医疗 prompt 主观对比：
- `medical500, r=8`：虽然已经有重复和冗长，但多数回答还保留了基本结构。
- `medical500, r=16`：开始出现更明显的长句堆砌、概念外延过度和局部循环，主观质量更差。
- `medical3800, r=8`：仍有模板化，但整体还能维持在“可读、可交付”的边缘。
- `medical3800, r=16`：退化最明显，多个问题上出现高频短语机械重复，例如“通过血液”“需要及时去医院”“刺激性的食物”等，已经接近明显生成崩坏。

因此当前最稳的解释不是“`r=8` 容量不够”，而是：
- 当前瓶颈主要在偏好数据的质量、覆盖和分布，而不是 rank 太小。
- 更高 rank 在这组医疗偏好数据上更像是在放大噪声、模板偏好和局部错误模式。
- 对 `0.5B` 这条 DPO 线来说，至少在当前数据和超参下，`r=8` 已经够用，`r=16` 没有带来额外收益，反而破坏了 benchmark 和主观生成质量。

一句话总结：**LoRA rank 变大并没有救回 DPO，反而进一步证明当前主导效果的核心变量是偏好数据本身，而不是单纯增加参数化容量。**



## 项目最终可讲结论树

### 1. 最顶层结论
- 这套医疗 LLM 项目里，**当前最可靠、最可解释的正向收益来自数据分布对齐**，不是单纯增加偏好训练或堆更复杂的 RLHF。
- `SFT -> RM -> DPO -> PPO` 这条链我已经完整跑通，因此工程闭环是成立的；但从最终 benchmark 来看，**工程链路跑通不等于效果自然变强**。

### 2. 最强正向结果来自哪里
- 最强结果来自 `Random SFT(500)` vs `Retrieved_t70 SFT(207)` 这组对比。
- 在统一 CEval 上：
  - `basic_medicine`：`0.5789 -> 0.5789`
  - `clinical_medicine`：`0.4545 -> 0.5000`
- 这说明：**数据分布更贴目标任务，比单纯扩大样本或盲目做偏好对齐更有效。**

### 3. DPO 这条线最后说明了什么
- 三组 DPO 对比：
  - `old500`：`0.4737 / 0.5000`
  - `medical500`：`0.4737 / 0.4091`
  - `medical3800`：`0.5789 / 0.5000`
- 主观样例对比也一致：
  - `old500` 可读性反而相对最稳。
  - `medical500` 重复、循环、啰嗦最明显。
  - `medical3800` 比 `medical500` 稳，但更多是在“把退化拉回 baseline”，而不是明显超过 baseline。
- 结论：**把偏好数据换成医疗数据，不会自动带来更好结果；500 条不稳，3800 条能恢复，但当前仍没有超过最强 SFT 基线。**

### 4. LoRA rank 消融最后说明了什么
- `r=8` vs `r=16` 的统一 CEval 和固定 10 条 prompt 对比都表明：`r=16` 更差。
- 特别是 `medical3800`：
  - `r=8`：`0.5789 / 0.5000`
  - `r=16`：`0.4737 / 0.4091`
- 主观上 `r=16` 还出现更严重的短语循环和生成崩坏。
- 结论：**当前瓶颈不在 LoRA 容量太小，而在偏好数据的质量、覆盖和分布。**

### 5. PPO 这条线最后说明了什么
- PPO 最小闭环已经完整跑完：RM merge 成功，PPO 训练完成，模型保存成功，后续 CEval 也跑通了。
- 统一 CEval 结果：
  - `SFT`：`0.5789 / 0.5000`
  - `PPO`：`0.5789 / 0.5000`
- 同时 PPO 训练和样例里暴露出：高 KL、right-padding 告警、边界污染、中英混杂。
- 结论：**PPO 当前最准确的定义是 RLHF 工程闭环验证成功，但没有形成额外 benchmark 收益。**

### 6. 这个项目最终想说明的核心判断
- 决定效果的核心变量，不是“模型更大”“LoRA rank 更高”或“方法更复杂”本身。
- 真正更关键的是：
  - 数据是否高质量
  - 数据是否和目标评测分布对齐
  - 偏好数据是否覆盖稳定
  - 训练目标是否真的对应你想优化的 benchmark
- 所以这版项目最后最有说服力的技术判断是：
  - **数据分布对齐 > 盲目扩数据**
  - **高质量偏好数据 > 只换成医疗标签的数据**
  - **稳定可解释的 baseline > 复杂但没有收益的后处理链路**

### 7. 面试时一句话收束
> 我把 `SFT -> RM -> DPO -> PPO` 这条医疗 LLM 对齐链完整跑通了，但最终发现最稳定、最可解释的收益来自数据分布对齐，而不是更复杂的偏好优化或更高的 LoRA 容量。这让我对“什么变量真正决定效果”有了更清晰的判断：不是方法名字更高级，而是数据质量、覆盖和目标分布是否匹配。
