# 三、项目一：医疗大模型训练与评测闭环（重点深挖）

## 1. 项目背景与目标定义

### 1.1 先不看简历，你用 2 分钟把这个项目完整讲一遍

**答：**

这个项目本质上是在 MedicalGPT 框架上，围绕一个轻量中文基座模型，搭了一条**医疗领域训练与评测闭环**。项目背景是：通用小模型虽然有基本指令跟随能力，但在医疗问答、病例分析、临床建议这种任务上，往往存在两个问题，一是**医学知识密度不够**，二是**回答格式不稳定、容易重复或结构不完整**。所以我想做的不只是单点 SFT，而是一整条链路：**数据构造 → SFT → 偏好对齐 → 标准化评测**。这个定位在你的笔记和简历里都是一致的。 

数据方面，我当前这轮形成完整实验闭环的主数据源，主要是 `shibing624/medical` 的中文医疗问答和偏好数据，以及 MedicalGPT 仓库内的小样本数据；`HealthAI-2025` 更多是项目背景和后续计划引入的结构化病例来源。换句话说，当前已经拿到的 CEval 消融结果主要来自 `shibing624/medical` 候选池召回，而不是直接来自 HealthAI 原始病例。

整个项目我分成了四个阶段：

* **第一阶段：数据构造与分布对齐**
  我先发现随机采样医疗 SFT 数据并不能稳定提升 CEval 医疗子任务，于是改成以 **CEval 医疗验证集作为目标分布锚点**，用 BGE 系列中文 embedding 模型做语义召回，从大规模医疗候选池中筛出更贴近目标任务分布的样本。当前真实实验是用 `BAAI/bge-small-zh-v1.5` 在 `1k/5k/50k` 候选池子集上逐步验证这条路线，最终召回筛选版本在 `clinical_medicine` 上从 `0.4545` 提升到 `0.5000`，提升约 `4.55pp`。如果继续扩展到更大规模候选池，我会再切到 `bge-large-zh` 这类更强 embedding 模型。

* **第二阶段：SFT**
  在 MedicalGPT 框架下做监督微调，使用 LoRA、bf16、gradient checkpointing，在单卡 4090 上完成训练。更准确地说，SFT smoke test 在 24G 4090 上峰值显存约 `85%`，而后续 RM、DPO 和消融主线主要在 48G 4090 上完成，其中 DPO 峰值显存约 `61.9%`。所以这里真正想强调的不是某一个绝对峰值，而是这套参数高效训练链路在单卡环境下可复现、可迭代。

* **第三阶段：偏好对齐**
  我分别跑了 **Reward Modeling** 和 **DPO** 两条线。RM 主要是验证偏好打分链路是否成立，使用的是 Bradley–Terry 风格的 pairwise loss；DPO 则从合并 LoRA 后的 SFT 初始化模型继续训练，重点改善回答的稳定性、结构完整性和重复崩坏问题。 

* **第四阶段：评测闭环**
  我基于 `lm-evaluation-harness` 建了 CEval 医疗子任务的标准化评测流程，同时配合小样本人工对比，避免只看训练 loss。笔记里已经给出统一 CEval 的对比结果：`Random SFT` 和 `Retrieved_t70 SFT` 在 `basic_medicine` 上持平，在 `clinical_medicine` 上从 `0.4545` 提升到 `0.5000`。

最后结果上，我不会把它讲成“全面大幅提升”，而会更诚实地总结成三点：

1. **数据分布对齐是有效的**，至少在更贴近临床分布的 `clinical_medicine` 子任务上有正收益。
2. **DPO 对生成稳定性有帮助**，缓解了重复崩坏和结构不完整，但不一定直接提升 CEval 这种知识型 benchmark。
3. **项目真正的价值在闭环**：你不是只会“跑个 SFT”，而是能解释为什么数据这样构造、为什么对齐有效、为什么评测结果这样变化。

### 1.2 你为什么选的是 Qwen2.5-0.5B，而不是更大的模型？

**答：**

这是一个典型的**资源约束下的工程权衡**。

第一，项目目标不是一开始冲绝对 SOTA，而是做一条**可复现、可解释、可完整跑通的全链路**。如果基座一开始就上 3B、7B 甚至更大模型，那么 SFT、RM、DPO、统一评测全部做下来，训练成本和调参成本会显著上升，不利于快速形成闭环。你的笔记里其实明确强调过：先用小基座把链路跑通，再逐步放大模型或样本规模。

第二，`0.5B` 这个量级对单卡非常友好。我的真实记录是：24G 4090 上可以完成 SFT smoke test，48G 4090 上可以稳定完成 RM、DPO 和后续消融，所以这个规模非常适合做大量 ablation，包括随机采样 vs 召回筛选、SFT vs DPO 这类控制变量实验。
对面试来说，这个回答会比“因为我机器不够”更成熟：**我优先保证实验设计完整性，而不是盲目追大模型。**

第三，小模型更适合凸显你这个项目的真正亮点。因为你的亮点不在“参数量大”，而在：

* 数据分布对齐是否有效
* 偏好对齐是否改善回答质量
* 评测闭环是否可信

这些问题在小模型上反而更容易看清楚因果关系。大模型可能 baseline 就很强，反而掩盖数据构造的贡献。

第四，从研究方法上说，小模型是更好的“实验载体”。做 ablation 最怕的就是变量太多，而更大的模型会同时引入更多变量：训练更慢、超参更敏感、显存更吃紧、评测周期更长。用 0.5B 先把问题形式化，再决定是否扩到 3B，是更合理的研究路径。

**八股原理可展开：**

* **边际收益递减**：模型越大，单位参数带来的领域提升不一定线性增加。
* **实验优先级**：先验证“方法有没有效”，再追求“模型够不够大”。
* **工程闭环优先**：对于面试项目，能完整讲清 SFT→RM→DPO→评测，比单点报一个大模型分数更有说服力。

## 2. 数据构造与分布对齐

### 2.1 你说随机采样 SFT 数据会导致 CEval 医疗指标不升反降。你最早是怎么发现这个问题的？

**答：**

最早我是通过**控制变量实验 + 统一 benchmark 观察**发现的。

一开始比较直觉的做法是：既然要做医疗领域适配，那就从医疗数据里随机抽一批样本做 SFT，理论上应该比通用基座更适合医疗任务。但真正跑完之后，我发现 CEval 医疗子任务并没有稳定上涨，这和预期不一致。简历里已经把这个现象概括为“随机采样 SFT 数据导致 CEval 医疗指标不升反降”。

后面在笔记里，我把这个问题形式化成了一组更严谨的 ablation：
做 `Random SFT` 和 `Retrieved SFT` 两组控制变量实验，统一在 `ceval-valid_basic_medicine` 和 `ceval-valid_clinical_medicine` 上比较。结果表明，随机采样并没有在临床医学任务上体现出优势，而经过分布对齐筛选的 `Retrieved_t70` 在 `clinical_medicine` 上涨到了 `0.5000`。

所以面试时可以这样讲：

> 我不是靠“感觉”发现这个问题的，而是通过 benchmark 结果反推出来的。最开始随机抽医疗数据做 SFT 后，医疗任务指标并没有如预期上涨，说明“数据是医疗的”不等于“数据分布就对”。后面我通过控制变量实验验证，问题更可能出在训练数据与目标任务的分布不对齐。

### 2.2 你为什么认为问题出在“数据分布不对齐”，而不是训练超参、模型容量或者评测波动？

**答：**

这是基于**排除法 + 现象一致性**判断出来的。

先说为什么不是单纯的训练超参问题。
如果问题主要来自学习率、batch size、LoRA rank 之类的训练超参，那么它通常会表现为：

* loss 波动异常
* 训练不稳定
* 不同任务一起涨或一起跌
* 改超参后整体表现明显变化

但你这个项目里更突出的现象是：**训练链路本身是稳定跑通的**，而且统一评测后发现不同医疗子任务的变化并不一致：`basic_medicine` 持平，`clinical_medicine` 提升。
这更像“样本分布更贴近某类任务”，而不是训练整体出了问题。

再说为什么不是模型容量问题。
如果是模型太小导致的，那么你无论随机采样还是召回筛选，理论上都应该一起受限，不太会出现“只换一种数据选择方式，某个临床子任务就有改善”的情况。现在观察到的事实恰恰相反：模型没换、训练框架没换，主要变量是数据选择方式，而指标发生了结构性变化，这就更支持“问题在数据分布”。

再说为什么不是评测波动。
确实，CEval 单个子任务样本量不大，存在方差，这是必须承认的。八股文里也提到 CEval 本身有样本量有限、静态 benchmark 的局限。
但如果每次实验都只靠波动解释，就无法支撑任何工程结论。更稳妥的做法是：看变化方向是否和数据构造逻辑一致。你的结果正好符合逻辑——更贴近临床分布的召回数据，对 `clinical_medicine` 更有帮助，而对偏基础知识的 `basic_medicine` 持平。这个现象是有解释力的。

所以可以这样答：

> 我不是说训练超参、模型容量、评测方差完全没影响，而是从控制变量结果看，最有解释力的主因是数据分布不对齐。因为在模型和训练链路基本不变的前提下，数据筛选方式一变，临床子任务就出现了方向一致的提升，这更符合 domain mismatch 的解释。

### 2.3 为什么选 CEval 验证集作为目标分布锚点？它有什么代表性？有什么局限？

**答：**

选 CEval 验证集做锚点，核心是因为它满足两个条件：
**一是目标明确，二是工程上可操作。**

所谓目标明确，就是我最终希望优化的是医疗 benchmark 表现，尤其是 `basic_medicine` 和 `clinical_medicine` 这类子任务。那最自然的思路就是：用目标任务本身的输入分布，去反向筛训练数据。你的笔记里也是明确这样设计的：把 `ceval-valid_basic_medicine` 和 `ceval-valid_clinical_medicine` 作为目标分布锚点。

所谓工程上可操作，是因为 CEval 题目天然可以统一表达成文本：
`题干 + 选项A/B/C/D`，而且不带答案。这样可以直接做 embedding，构造一个“目标分布向量库”，再和候选 SFT 样本做相似度匹配。这个流程在你的笔记里写得很完整。

它的代表性主要体现在：

* 对医疗知识和临床场景有一定覆盖
* 是中文 benchmark，和中文医疗问答任务更匹配
* 便于后续做统一评测闭环

但局限也必须主动说：

1. **它是选择题，不是开放式问答。**
   所以它更像知识和判断题，不完全代表真实医疗对话质量。

2. **样本量不大，方差存在。**
   单个子任务题目数有限，不适合过度解读细小涨跌。

3. **容易把优化目标“拉向 benchmark 风格”。**
   也就是面试官会质疑：你是不是只是让训练数据更像 CEval，而不是更像真实医疗问答。

所以成熟回答应该是：

> 我选 CEval 验证集做锚点，不是因为它完美，而是因为它是我当前最明确、最可操作的目标分布代理。它能帮助我做可解释的数据筛选和控制变量实验；但我也承认它只是目标分布的一个 proxy，不代表全部真实医疗场景，所以后面必须再配合主观问答评测。

### 2.4 你这里用 bge-large-zh 做向量化，为什么选它，不选别的 embedding 模型？

**答：**

我选 BGE 系列中文 embedding 模型，主要基于三点考虑。当前真实实验里实际跑通的是 `bge-small-zh-v1.5`，而 `bge-large-zh` 更适合作为后续放大候选池时的增强方案：

**第一，中文语义检索能力强。**
这个项目的核心不是生成，而是先做**语义分布对齐**。所以 embedding 模型最重要的能力是：能稳定表示中文问答、症状、疾病、处理建议这类语义近邻关系。当前我实际使用的是 `BAAI/bge-small-zh-v1.5`，因为它在 1k/5k/50k 子集验证阶段吞吐更友好；如果后续把候选池进一步扩大，再切换到 `BAAI/bge-large-zh-v1.5` 会更合理。

**第二，适合“题干/指令侧”的相似度匹配。**
这个项目不是做多模态，也不是做长文档检索，更不是代码 embedding，所以没必要上特别复杂的模型。BGE 这类中文文本 embedding 已经足够胜任“CEval 题目 ↔ 医疗问答指令”之间的相似度筛选。

**第三，可解释性更好。**
用统一语义空间来做候选样本筛选，比手写关键词规则或者用生成模型主观判断“这条像不像医学题”更容易解释，也更方便做阈值扫描和消融。

如果面试官继续追问“为什么不是别的”，你可以答：

### 2.5 你对 200w 条医疗数据做向量化，具体怎么做的？是离线批量编码吗？怎么处理吞吐和存储问题？

**答：**

这件事我会分成两层来讲：**工程方案上，200w 级离线向量化完全可行；项目事实层面，我实际验证到的是 `1k/5k/50k` 候选池子集，而不是已经完成了 200w 全量筛选。**

先说工程实现，如果真做 200w 级候选池，我会明确采用**离线批量编码 + 向量落盘复用**，而不是在线逐条算。更具体的流程一般是：

1. **先统一样本表示**
   只编码 `instruction/question` 这一侧，不把 `output` 拼进去。这样做的原因是回答里往往混有风格模板、语气词和冗余解释，容易把“写法相似”误当成“任务分布相似”。你的笔记里也是按这个思路设计的：优先让 embedding 表示问题语义，而不是答案风格。

2. **离线分 batch 编码**
   把候选池按 shard 切分，比如按固定条数或文件块拆开；每个 shard 再按 batch 做 embedding 前向。这样可以把最重的计算集中在一次性的离线特征工程阶段，而不是每次改阈值、改锚点都重新算一遍。

3. **向量和元数据一起持久化**
   编码后至少保留两类东西：

   * 向量矩阵本身，常见是 `.npy`、`.pt` 或者直接建 FAISS 索引
   * `sample_id -> 原始文本/来源文件` 的映射，保证召回后能回溯样本内容

   如果按 `bge-large-zh` 的 `1024` 维向量粗略估算，`200w * 1024 * 4 bytes`，`float32` 大约是 `7.6GB`；如果改成 `float16`，大约 `3.8GB`。再加上索引和元数据会更大一些，但整体仍然在可接受范围内，所以这件事的瓶颈主要是编码吞吐，不是“存不下”。

4. **召回阶段只编码锚点**
   CEval 医疗子任务的锚点规模很小，所以检索阶段只需要对锚点题目做小规模编码，然后跟离线向量库做 cosine 相似度匹配、最近邻检索或阈值筛选。也就是说，重计算发生在前面的离线 embedding，后面的筛选其实相对轻量。

从项目实际进度看，我更稳妥的说法不是“我已经把 200w 全量都向量化完并筛好了”，而是：

* 我已经在 `1k/5k/50k` 候选池子集上验证了这条分布对齐召回路线的有效性。
* 随着候选池扩大，召回样本数和最大相似度是稳定上升的。
* 在统一 CEval 下，最终 `Retrieved_t70 SFT(207)` 相比 `Random SFT(500)`，`basic_medicine` 持平 `0.5789`，`clinical_medicine` 从 `0.4545` 提升到 `0.5000`。
* 同时，我把 200w 级候选池的离线批量向量化方案设计清楚了，具备继续扩展的工程可行性。

所以面试里最稳的一种答法是：

> 工程上，200 万条候选样本的做法一定是离线批量 embedding：只编码 instruction/question，按 batch 和 shard 分块前向，向量落盘并保留样本映射，后续只对 CEval 锚点做小规模编码，再基于 cosine 或 ANN 做筛选。实际实验上，我先在 1k、5k、50k 候选池子集验证了这条路线的有效性，并没有把它包装成已经完成了 200w 全量筛选；我会更准确地说，这是一个已经在子集上验证有效、并且可扩展到 200w 级的工程方案。

**八股原理：**

* 大规模向量化本质上是离线特征工程，不适合在线逐条实时计算。
* 吞吐瓶颈主要在 embedding 前向阶段，检索阶段反而相对轻。
* 存储设计的核心不是只存向量，而是同时维护可回溯的样本索引。
* 更严谨的项目表述应该区分“方案可扩展到 200w”和“实验已经做到 200w”这两件事。

### 2.7 阈值如果调到 0.6 或 0.8，预期会发生什么？

**答：**

这是典型的**召回率—精确率 trade-off**。

* **调到 0.6**：
  召回样本数会明显增多，覆盖更广，但同时噪声也会变多。也就是说训练集会更“大”，但与目标分布的贴合度下降，容易把一些“泛医疗”但不够贴近 CEval 临床题风格的样本也带进来。

* **调到 0.8**：
  纯度会更高，但样本数可能极少，甚至不足以支撑有效训练。你的真实实验里 `t80` 在 50k 候选池上也只筛出 1 条，这已经说明 0.8 对当前设定来说过严。

所以从原理上讲：

* 阈值低：高召回、低精度
* 阈值高：低召回、高精度

面试时可以把这个讲成一句工程判断：

> 0.6 更像“保覆盖”的策略，适合候选池很小或者想快速做第一版训练；0.8 更像“高纯度 case study”的策略，但不适合当前规模做主实验。我的实验结果也验证了这一点，所以我最后选了 0.70 做主线。

### 3.9 为什么开 gradient checkpointing？它具体牺牲了什么、换来了什么？

**答：**

`gradient checkpointing` 的本质是**用计算换显存**。

原理上，它不会在前向传播时保存所有中间激活，而是在反向传播时把部分前向重新算一遍。这样能显著降低显存占用，但代价是训练速度会变慢。你的笔记里对 RM 和 DPO 都是这样解释的。

为什么这个项目要开？因为你要在单卡 4090 上同时跑：

* SFT
* RM
* DPO
* 评测

而且还希望保留足够的序列长度和 batch 规模。在这种场景下，checkpointing 是非常典型的工程手段。简历里也把它当作显存控制关键点之一写进去了。

所以回答可以是：

> 我开 gradient checkpointing，主要是为了在单卡上把更长序列和更稳定的 batch 跑起来。它牺牲的是一部分训练速度，换来的是显存占用显著下降。对这个项目来说，训练吞吐不是第一优先级，能稳定把全链路跑通更重要。

### 4.6 Bradley–Terry 模型的 loss 公式你能写出来吗？每一项代表什么？

**答：**

可以。你项目里 RM 采用的是 Bradley--Terry 风格的 pairwise preference loss，本质公式可以写成：

```tex
\mathcal{L}_{RM} = -\log \sigma\big(r_\theta(x, y_w) - r_\theta(x, y_l)\big)
```

其中：

* `x`：问题或上下文
* `y_w`：chosen，也就是更优回答
* `y_l`：rejected，也就是较差回答
* `r_\theta(x, y)`：奖励模型对这条 `(问题, 回答)` 的打分
* `\sigma`：sigmoid，把分差映射成概率

口头解释时我会直接说：这个损失的目标，就是让 `chosen` 的分数高于 `rejected`；如果 `r_\theta(x, y_w) - r_\theta(x, y_l)` 越大，loss 就越小，说明模型越认同“这条优回答应该排在前面”。

直觉上就是：
我们希望 chosen 的分数比 rejected 高，所以优化目标是让 `r_\theta(x, y_w) - r_\theta(x, y_l)` 尽可能大。
如果 chosen 分数已经比 rejected 高很多，loss 就会变小；如果排序错了，loss 就会变大。

面试里你可以再加一句：

> 这个式子本质上就是把偏好学习转成二元排序学习问题。Bradley–Terry 假设回答优劣可以由标量得分差决定，是 RLHF 和偏好建模里很经典的建模方式。

### 4.7 奖励模型训练时，你如何避免 reward model 只学到长度偏好、模板偏好这些伪特征？

避免 RM 学伪特征，核心思路有三类：

1. **数据层面**
   尽量让 chosen 和 rejected 在长度、格式上不要差得过分明显，否则模型很容易学到“更长更好”这类伪规律。

2. **模板一致性**
   chosen / rejected 都按同一模板拼装输入，避免模型只根据 prompt 格式差异来打分。你的笔记里反复强调 template_name 要一致。

3. **外部验证**
   不能只看 RM 的 train/eval loss，还要用小样本人工抽查，确认它排序的依据是内容质量而不是表面形式。

面试里建议答：

> 避免伪特征的关键是让偏好差异尽量集中在“内容质量”而不是“表面格式”上。当前这版我主要通过模板一致和数据集本身的 chosen/rejected 设计来控制这个问题；如果继续深入做 RM，我会专门检查长度偏好和格式偏好是否过强。

### 4.10 DPO 的训练目标公式你能口头解释一下吗？

**答：**

可以。DPO 的标准目标我会写成下面这个形式：

```tex
\mathcal{L}_{DPO} = -\mathbb{E}\left[
\log \sigma \left(
\beta \log \frac{\pi_\theta(y_w|x)}{\pi_{ref}(y_w|x)}
-
\beta \log \frac{\pi_\theta(y_l|x)}{\pi_{ref}(y_l|x)}
\right)
\right]
```

口头解释可以这样讲：

> DPO 的核心思想是：
> 对同一个问题 `x`，我希望当前策略模型 `\pi_\theta` 相对于参考模型 `\pi_{ref}`，更偏向 `chosen` 回答 `y_w`，而更不偏向 `rejected` 回答 `y_l`。
> 换句话说，我不是单独去拉高 `chosen` 的概率，而是要求“`chosen` 相对 reference 的优势”要大于“`rejected` 相对 reference 的优势”。

其中：

* (\pi_\theta)：当前要训练的策略模型
* (\pi_{ref})：冻结的参考模型
* (y_w)：chosen
* (y_l)：rejected
* (\beta)：控制偏好约束强度的系数

直觉上 DPO 是把 RLHF 里的“奖励最大化”问题，转换成一个更稳定的监督式偏好优化问题。

### 4.11 DPO 里的 reference model 是谁？为什么必须有它？

**答：**

在你这条链路里，reference model 就是**冻结的 SFT 初始化模型**，也就是 DPO 开始训练时的起点模型，不再更新，只作为概率比值的参照。
你笔记里也明确写了 DPO 是从 “合并 LoRA 权重后的 SFT 初始化模型” 起步。

为什么必须有它？因为 DPO 不是简单地让 chosen 概率更高，而是要控制“相对参考策略的偏移”。
如果没有 ref model，策略模型可能会为了偏好对过度偏移，出现类似 reward hacking 的问题。
有了 ref model，DPO 本质上就在说：

* 对 chosen，可以比原来更偏好一点
* 对 rejected，可以比原来更不偏好一点
* 但不是无限制偏离原始 SFT 分布

所以 ref model 本质上起到了和 PPO 里 KL 约束类似的“稳定器”作用。

### 4.12 你说是以“合并 LoRA 权重后的 SFT 初始化模型”为起点去做 DPO，为什么要先 merge 再训？

**答：**

这是一个很典型的工程选择。

你的笔记里明确把 DPO 的基座写成 `./outputs-local-sft-smoke-merged`，也就是先把 SFT 的 LoRA 合并回基座，再作为 DPO 的起点。

为什么先 merge？主要有三个原因：

1. **得到一个干净、完整的初始化模型**
   merge 后，SFT 结果被固化为一个普通 `from_pretrained` 可加载的模型目录，后续 DPO 不需要再额外依赖旧的 adapter 结构。

2. **减少多层 LoRA 叠加的复杂性**
   如果不 merge，继续在 adapter 上叠 adapter，参数管理和加载逻辑会更复杂。

3. **更便于后续推理和评测**
   merge 后模型可以直接拿去做 CEval、做推理 sanity check，不需要每次再组合 base + adapter。

所以你可以答：

> 我先 merge，是为了把 SFT 阶段的能力固化成一个干净的初始化模型，避免后面 DPO 再叠多层 adapter，简化训练和评测链路。这是更稳妥的工程做法。

### 4.13 如果不 merge，直接带 LoRA 继续 DPO，有什么问题吗？

**答：**

不是绝对不行，但会带来工程复杂度和实验可追溯性的问题。

主要问题有三类：

1. **参数状态更复杂**
   你会同时依赖 base model + SFT adapter + DPO adapter，后续很难清晰区分每层修改来自哪里。

2. **加载与部署更麻烦**

3. **实验不利于复现**

所以答法可以是：
