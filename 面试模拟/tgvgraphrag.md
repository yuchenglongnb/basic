# TGV 工艺-缺陷 GraphRAG 方案说明

## 1. 项目定位

本项目的目标不是做一个通用聊天机器人，而是围绕 TGV 基板通孔制造场景，建设一套面向缺陷追溯、工艺评估和优化建议生成的知识增强系统。

系统解决的核心问题包括：

- 将缺陷现象、设备状态、工艺步骤、工艺参数、检测结果和专家经验组织成统一知识网络
- 支持从“缺陷现象”反推“候选工艺原因”和“优先排查路径”
- 支持从历史文档、日志、追溯报告中召回相似案例和证据链
- 基于图谱与大模型输出可解释的工艺评估意见和优化建议

因此，这个项目更准确的定义是：

- 以问答为入口
- 以工艺追因为核心
- 以知识图谱和 GraphRAG 为增强
- 以大模型为推理和表达层

## 2. 为什么选 GraphRAG 而不是普通 RAG

TGV 场景不适合只靠普通向量检索，原因主要有三点：

1. 问题通常是跨文档、多跳、因果链式的。  
例如“某批次孔壁粗糙上升，优先排查激光参数还是后段刻蚀”，答案往往分散在工艺文档、缺陷报告、设备日志和专家分析中。

2. 需要做全局理解而不只是片段匹配。  
很多问题不是找一句原文，而是从多个证据中总结“高概率原因”“典型路径”“建议动作”。

3. 工业知识高度结构化。  
设备、参数、工序、缺陷、原因、措施之间天然存在显式关系，适合先建图再检索。

因此项目采用 GraphRAG 的核心思路：

- 在索引阶段，将多源异构数据抽取为实体、关系、事件和证据
- 通过图结构把分散信息组织起来
- 在查询阶段，先围绕问题做实体定位和子图召回，再让大模型基于结构化上下文进行推理和生成

## 3. 场景问题抽象

从业务上看，这个系统需要回答的问题可以抽象为四类：

### 3.1 缺陷解释

- 某种缺陷的定义是什么
- 该缺陷一般表现在哪些检测指标上
- 典型形态特征是什么

### 3.2 缺陷追因

- 该缺陷与哪些工艺参数偏差相关
- 优先排查哪些工序、设备或配方
- 是否存在典型的因果路径

### 3.3 相似案例检索

- 历史上是否出现过相似缺陷
- 这些案例最后归因到什么问题
- 采取过哪些措施，效果如何

### 3.4 工艺评估与建议

- 当前工艺窗口是否存在风险
- 哪些参数建议优先调整
- 调整建议的依据来自哪些规则、案例或文档证据

## 4. 数据范围与输入来源

系统数据不只是一类工艺文档，而是多源异构知识组合。

### 4.1 文档类

- 工艺流程文档
- SOP 和作业指导书
- 配方说明书
- 设备说明书与维护手册
- 缺陷追溯报告
- 缺陷成因分析报告
- 点检记录和维护记录
- 会议纪要和专家结论

### 4.2 结构化业务数据

- 批次信息
- 板信息
- 孔位信息
- 工艺步骤与配方
- 参数阈值配置
- 参数采样记录
- 缺陷检测结果
- 人工复判结果

### 4.3 日志和事件流

- 设备运行日志
- 告警日志
- 工艺执行记录
- MES/设备事件流

### 4.4 图像与视觉输出

- 原始缺陷图像
- 图像路径和图像元数据
- 孔坐标和 ROI 信息
- 视觉检测框、分割结果、分类结果
- 缺陷置信度和人工审核结果

需要强调的一点是：GraphRAG 不直接替代视觉检测模型。图像通常由外部视觉模型先完成识别、定位、分割和分类，再将结构化输出作为图谱实体和事件的一部分接入系统。

## 5. 知识图谱建模思路

项目中的图谱不是泛化百科图谱，而是面向工艺追因场景的领域图谱。建模时采用“实体 + 事件 + 属性 + 证据”的思路。

### 5.1 核心实体

- ProductLot：批次
- Board：板级对象
- Hole：孔位对象
- Tool：设备
- Recipe：配方
- ProcessStep：工艺步骤
- ProcessParameter：工艺参数
- Material：材料/试剂
- DefectType：缺陷类型
- DefectCause：缺陷原因
- ActionMeasure：措施
- EnvironmentFactor：环境因素
- ImageAsset：图像元数据
- Document：文档
- ExpertRule：专家规则

### 5.2 核心事件

- ProcessEvent：工艺执行事件
- ParameterSampleEvent：参数采样事件
- DetectionEvent：检测事件
- AlarmEvent：告警事件
- MaintenanceEvent：维护事件
- InferenceEvent：推理或追溯事件

### 5.3 核心关系

- LOT_HAS_BOARD
- BOARD_HAS_HOLE
- BOARD_USES_RECIPE
- STEP_USES_TOOL
- STEP_USES_MATERIAL
- STEP_HAS_PARAMETER
- EVENT_OCCURS_AT_STEP
- EVENT_ON_BOARD
- EVENT_ON_HOLE
- DETECTS_DEFECT
- DEFECT_HAS_CAUSE
- CAUSE_HAS_MEASURE
- DEFECT_RELATED_TO_PARAMETER
- DEFECT_RELATED_TO_STEP
- EVENT_PRECEDES_EVENT
- EVENT_CAUSES_EVENT
- DOCUMENT_SUPPORTS_RELATION
- INFERENCE_REFERENCES_ENTITY

### 5.4 为什么不只用三元组

工业知识里很多关系不是无条件成立的，而是在特定工序、参数区间、环境条件、检测条件下成立。因此项目实际建模不是单纯静态三元组，而是更接近“三元组 + 条件上下文 + 证据”的扩展表示。

例如：

- 高激光功率密度 -> may_cause -> 孔壁重铸层增厚
- 条件：薄玻璃基板、特定扫描速度区间
- 证据：某份工艺分析报告的具体段落

这样的表示比无条件关系更适合工业场景，也能减少错误泛化。

## 6. 模型配置与选型原因

结合当前仓库配置和项目设计，系统中的模型不是“一模型包打天下”，而是按步骤拆分职责。

### 6.1 当前工程配置

从当前仓库 [settings.yaml](/mnt/data2/ycl/graphrag/settings.yaml) 来看，核心配置如下：

- 生成模型：`Qwen3-14B`
- 查询生成模型：`Qwen3-14B`
- Embedding 模型：`BGE-M3`
- 模型服务：本地 OpenAI 兼容接口 `http://127.0.0.1:11434/v1`
- 向量库：`LanceDB`
- 文本切块：`size=512`，`overlap=50`
- 并发控制：`concurrent_requests: 1`

项目主用模型组合统一表述为 `Qwen3-14B + BGE-M3`。其中 `Qwen3-14B` 负责知识抽取与推理生成，`BGE-M3` 负责语义检索；在工程部署和性能调优阶段，也测试过其他规模的 Qwen 模型，用于平衡显存占用、吞吐和稳定性。

### 6.2 文档切块与预处理阶段

这一阶段通常不依赖大模型，主要依赖规则处理和 tokenizer。

使用内容：

- token chunking
- 术语归一化规则
- 主键对齐规则
- 文本清洗脚本

选型原因：

- 这一步是确定性数据工程问题，不适合让大模型参与
- 规则化处理更稳定、更便宜、更容易复现

### 6.3 知识抽取阶段使用的模型

主要模型：

- `Qwen3-14B`

主要任务：

- 从工艺文档、缺陷报告、维护记录中抽取实体、关系和事件
- 生成实体和关系描述
- 对缺陷原因、措施、参数、工序进行结构化抽取

选型原因：

- 工业文档中存在长句、条件句、半结构化描述、术语缩写，抽取任务比普通聊天更复杂
- 需要较强的中文理解能力和结构化输出能力
- 相比小模型，较大生成模型在复杂条件关系和弱格式文档上的抽取稳定性更好

### 6.4 向量化与检索阶段使用的模型

主要模型：

- `BGE-M3`

主要任务：

- 为文档块生成向量表示
- 为查询生成向量表示
- 支撑语义召回和相似案例召回

选型原因：

- 工艺文本、缺陷描述、专家经验在表达上差异较大，需要较强的语义泛化能力
- BGE-M3 对多语言、多粒度检索表现稳定，适合工业术语和长短文本混合场景
- 将检索与生成解耦，便于分别优化召回质量和答案质量

### 6.5 查询理解阶段使用的模型

项目方案中，这一阶段通常使用轻量模型或规则配合完成关键实体抽取。

候选模型：

- BERT 类实体抽取模型
- 规则词典 + 模式匹配
- 小型分类模型用于问题类型识别

主要任务：

- 从查询中识别缺陷类型、工艺参数、工艺步骤、设备、批次号、板号、孔号、时间范围
- 判断查询属于缺陷解释、工艺追因、相似案例还是优化建议

选型原因：

- 查询阶段强调高频、低时延、稳定，不适合每次都完全依赖大模型做开放式理解
- 关键实体类型相对可控，适合用轻量模型或规则做稳定锚点抽取
- 先抽锚点，再做子图召回，能显著降低后续噪声

### 6.6 最终推理与答案生成阶段使用的模型

主要模型：

- `Qwen3-14B`

主要任务：

- 基于问题、子图、证据片段、历史案例、规则信息生成结论
- 输出“结论 + 依据 + 建议”的结构化回答
- 对工艺建议进行自然语言解释

选型原因：

- 最终生成阶段不仅要“回答”，还要“解释为什么这么回答”
- 需要综合多条证据、多个关系路径和历史案例
- 工业场景里回答风格必须稳健，较强生成模型在多证据整合和长上下文组织上更合适

### 6.7 图像阶段涉及的模型边界

图像相关能力通常由外部视觉模型完成，而不是由 GraphRAG 本身负责。

候选模型：

- YOLO 系列检测模型
- 分割模型
- 缺陷分类模型

主要任务：

- 图像检测、定位、分割、分类
- 输出缺陷标签、置信度、坐标、图像路径等结构化结果

选型原因：

- 图像识别是专门的视觉任务，不适合让文本大模型硬做
- 视觉模型输出结果再进入图谱，更符合模块化系统设计

## 7. GraphRAG 索引阶段设计

索引阶段的目标，是把多源异构数据转成“可检索、可推理、可追溯”的图谱和向量索引。

### 7.1 索引阶段总体流程

1. 导入原始文档和业务数据
2. 按文档块进行切分
3. 用生成模型抽取实体、关系和事件
4. 汇总描述并做实体归一
5. 构建图关系和局部语义网络
6. 用 embedding 模型生成向量索引
7. 产出用于查询阶段的图谱和社区摘要材料

### 7.2 抽取阶段的二次开发点

与原生 GraphRAG 相比，项目主要做了以下定制：

- 将通用实体类型改造成工业领域 schema
- 修改抽取 prompt，强调保守抽取、证据绑定、条件约束
- 引入工艺事件和时间维信息，而不仅仅是静态实体关系
- 对缺陷原因、措施、参数、工序进行重点建模，服务后续追因和建议场景
- 对别名、缩写和同义词做归一化处理，减少图谱脏节点

### 7.3 为什么要保守抽取

工业场景最怕的不是漏一条知识，而是抽出一条表面合理但实际上错误的因果关系。因此抽取阶段的原则是：

- 原文无明确支持则不抽
- 不确定时宁可返回空
- 必须保留证据来源
- 关系必须满足 schema 校验

## 8. 查询阶段设计

当前配置中已经定义了四类查询能力：

- `local_search`
- `global_search`
- `drift_search`
- `basic_search`

面向 TGV 场景，查询链路建议组织为五步。

### 8.1 问题理解

输入通常是自然语言，比如：

- 最近某批次孔位偏移变多，优先排查什么
- 某类堵塞缺陷和刻蚀液浓度关系大吗
- 对于某板上的孔径过小，建议先看激光还是后蚀刻

首先要做问题类型识别，判断用户更偏向：

- 缺陷解释
- 原因追溯
- 相似案例查询
- 工艺优化建议

模型或方法：

- 轻量分类模型
- 规则模板
- 必要时由大模型补充语义判断

选型原因：

- 优先用轻量方法完成粗分类，成本低、响应快
- 只有在问题歧义较大时才引入大模型补充理解

### 8.2 关键实体抽取

在项目方案里，这一步可由轻量模型或规则配合完成，重点识别：

- 缺陷类型
- 工艺步骤
- 工艺参数
- 设备
- 批次/板号/孔号
- 时间范围

模型或方法：

- BERT 类实体抽取模型
- 规则词典
- 别名表归一

选型原因：

- 实体集合相对可控
- 高并发下时延比开放式生成更容易控制
- 先抽锚点更适合后续子图召回

### 8.3 子图召回与证据扩展

系统围绕关键实体做多种召回：

- 图邻域召回
- 文档证据召回
- 相似案例召回
- 参数和规则召回

使用模型：

- `BGE-M3` 用于语义召回
- 图关系规则用于邻域扩展

选型原因：

- 向量检索负责召回语义相近文本和案例
- 图规则负责补齐结构关系和局部路径
- 两者结合比纯向量检索更适合追因问题

### 8.4 结构化信息转自然语言上下文

图谱中的结构化内容并不适合直接丢给大模型，需要通过模板转写成自然语言证据段。典型转写包括：

- 某缺陷通常出现在某工序之后
- 某参数在什么区间异常时，与某缺陷相关性更高
- 历史上相似案例最终归因为某设备状态异常
- 某专家规则建议优先采取哪些措施

模型或方法：

- 模板系统
- 必要时小模型或大模型辅助压缩

选型原因：

- 模板化更可控，减少表述漂移
- 先转写再推理，能降低图数据与大模型之间的理解障碍

### 8.5 最终答案生成

最终输出应尽量是结构化的，而不是泛泛一段话。建议统一为三段式：

- 结论：高概率原因或评估结果
- 依据：对应证据链、案例、规则或关系路径
- 建议：优先排查项、优先调整项、风险提示

使用模型：

- `Qwen3-14B`

选型原因：

- 需要整合多条证据和多个关系路径
- 需要输出稳健、可解释、可读的自然语言结论
- 较强生成模型更适合多证据综合和长上下文组织

## 9. Local / Global / Drift / Basic 的场景分工

### 9.1 Local Search

适合局部实体和局部路径问题。

例如：

- 孔径过小常和哪些参数相关
- 某设备异常可能引发哪些缺陷

### 9.2 Global Search

适合全局总结型问题。

例如：

- 当前系统内最常见的几类工艺-缺陷关联是什么
- 某段时间内主要风险模式有哪些

### 9.3 Drift Search

适合探索性或逐步扩展问题，尤其是在用户问题较模糊时，从一组初始锚点向外扩展相关知识。

例如：

- 最近质量波动大，但还不确定主要是哪个工序出问题
- 某类新缺陷出现后，希望系统帮助探索潜在相关因素

### 9.4 Basic Search

适合事实性较强的简单问答，如定义、术语、单文档事实定位。

## 10. 模型服务与性能问题

### 10.1 为什么这个场景容易触发推理瓶颈

知识抽取和图谱生成阶段通常具有以下特点：

- 请求数量多
- 文本长度差异大
- 长时间运行
- Map 阶段和摘要阶段负载模式不同

这种负载容易导致推理服务出现：

- 尾延迟升高
- 队列堆积
- 长请求超时
- 显存缓存利用效率下降

### 10.2 为什么要从更轻量的本地服务迁移到更适合批处理的服务

如果系统长时间运行并承受批量抽取任务，推理服务不仅要“能跑起来”，还要能稳定处理大量不同长度请求。更适合工业索引场景的服务往往需要具备：

- 更好的 KV cache 管理
- 更好的 continuous batching
- 更好的长时间吞吐稳定性

因此，项目的工程化思路不是单纯换模型，而是把推理服务从“可用”升级为“可持续高吞吐”。

### 10.3 稳定性策略

项目在工程上建议至少配备以下机制：

- 指数退避重试
- 请求超时控制
- 并发数限制
- 索引阶段缓存
- 日志留痕和失败样本回放
- 模型服务健康检查

## 11. 图像与多模态边界

这个项目容易被误解成“GraphRAG 直接看图并推理”。更准确的边界是：

- 视觉模型负责图像层面的检测、分割、定位、分类
- GraphRAG 负责把视觉输出与文档知识、工艺事件、设备日志和专家规则连接起来
- 大模型负责做跨模态结果的解释、追因和建议生成

因此，图像在系统里主要以两种形式存在：

- 图像元数据：路径、采集时间、板号、孔号、相机信息
- 视觉结果：缺陷类型、置信度、检测框、分割区域、复判结果

## 12. 部署建议

### 12.1 一期部署目标

建议先做“离线建图 + 在线查询”的模式：

- 图谱和索引按批次、按小时或按日更新
- 查询侧支持秒级到十秒级响应
- 不直接做在线自动调参
- 输出以辅助决策为主，保留人工审核

### 12.2 基础组件

- 本地 LLM 服务
- 本地 Embedding 服务
- GraphRAG 索引和查询服务
- 向量库
- 结构化数据库
- 文件存储或对象存储
- 日志与监控

### 12.3 需要提前确认的环境约束

- GPU 型号与显存
- 数据规模和增长速度
- 图像存储体量
- 是否必须完全离线
- 是否允许模型更新
- 是否存在多角色权限要求

## 13. 一期最小可行交付范围

若以 MVP 为目标，建议一期只做以下闭环：

1. 导入工艺文档、缺陷报告、维护记录和部分日志
2. 建立基础工艺-缺陷知识图谱
3. 支持缺陷类型、工艺参数、工艺步骤相关问答
4. 支持批次级追溯分析
5. 支持输出证据链和建议
6. 保留图像元数据和视觉结果映射，不直接做复杂多模态推理

## 14. 二期可扩展方向

- 接入更多设备日志和在线事件流
- 支持孔级追溯
- 支持知识审核工作台
- 支持规则编辑和版本管理
- 支持相似案例的闭环反馈
- 支持准实时触发分析
- 引入更强的时序因果建模

## 15. 面试或汇报时可概括成的一句话

这个项目本质上是一个面向 TGV 制造场景的因果知识增强工艺评估系统：通过 GraphRAG 把工艺文档、日志、检测结果、专家经验和缺陷知识组织成可检索、可追溯、可解释的图谱，再结合大模型完成缺陷追因、工艺评估和优化建议生成。
