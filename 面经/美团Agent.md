# 一、整套面经的主线

如果把这套题串起来，本质是在问：

* 你能不能设计一个 **美团业务场景下可落地的大模型系统**
* 你对 **RAG、Agent、微调、推理优化** 是不是都真的懂
* 你是不是不仅会“调 API”，而是知道背后的 **算法原理和工程约束**

```text

-> 工具调用与 Agent 编排
-> 上下文管理 / 长对话 / 状态机
-> 推理优化 / 服务性能

```

# 二、一面（技术面）详细整理

## 1. RAG 架构设计：给美团酒店设计问答 RAG，怎么保证能准确回答设施、交通问题？

## 题目本质

考你能不能围绕一个真实业务场景设计 RAG，而不是只会说“向量检索 + 大模型”。

酒店问答场景的特点：

* **知识来源多样**：酒店基础信息、设施、政策、交通、周边、用户评价
* **问题类型不同**：事实类、规则类、主观总结类
* **信息时效性不同**：酒店设施变更、接送服务调整、早餐政策变化
* **答案要求高准确**：尤其“有无接机”“是否有停车场”“距离地铁多远”这类问题

---

## 标准回答框架

可以按这 6 层说：

### 1）数据分层建库

酒店问答不要把所有数据一锅炖，要分层：

* **结构化数据**：酒店设施、营业时间、停车场、接送服务、地址、经纬度、房型、政策
* **半结构化文本**：酒店介绍、设施说明、政策说明
* **非结构化文本**：用户评论、问答记录、客服 FAQ
* **动态信息**：临时政策、装修通知、服务变更

### 2）问题路由

先判断问题类型，再决定走哪条链路：

* **设施/政策/交通事实类**：优先查结构化知识库
* **评论总结类**：走评论检索 + 摘要总结
* **综合问题**：结构化结果 + 文本证据联合生成

### 3）混合检索

对文本部分做：

* 稠密向量召回：处理语义表达差异
* BM25 稀疏召回：处理设施名、地点名、专有词、数字

### 4）细粒度切块 + 父子索引

* 小块召回，提高命中精度
* 父块回填，保证语义完整

### 5）Rerank 精排

用 cross-encoder 或强 reranker 对候选文档重排，避免“召回到但排位不准”。

### 6）答案约束

生成时要求：

* 必须基于检索证据回答
* 若证据不足则明确回答“不确定”
* 优先引用结构化字段
* 对交通问题可把地理距离转成用户易懂表达，如“步行约 8 分钟”

---

## 八股原理

### 为什么酒店问答要“结构化优先”？

因为“有无游泳池”“是否可带宠物”“距机场多少公里”本质是确定性事实，最适合从结构化字段直接回答。
如果只靠评论和自然语言文本，容易出现：

* 信息不一致
* 历史评论过时
* 用户主观表述不可靠

所以最稳的策略是：

> **结构化事实做主干，文本做补充解释，评论做感知补充。**

---

## 可直接背诵版

> “酒店问答我会做一个分层 RAG。设施、地址、交通、政策这类高确定性问题优先查结构化知识库，评论和酒店介绍走文本混合检索。文本侧会做向量召回 + BM25 + Rerank，并采用父子 chunk 保证小块召回精度和大块上下文完整。最终生成时要求答案必须引用高置信证据，证据不足时允许拒答或保守回答。这样能同时保证设施、交通类问题的准确率和可解释性。”

---

## 追问点

### Q1：交通问题怎么设计更准？

答：

* 地址统一标准化
* 接入 POI / 地图服务
* 把“距离地铁站”“到机场时间”做结构化字段
* 对用户问“近不近”可转成时间/距离解释

### Q2：评论和酒店官方描述冲突怎么办？

答：

* 官方结构化信息优先
* 评论只做补充感知
* 如有时间戳，优先最新信息
* 模型回答时显式区分“官方信息”和“用户反馈”

## 2. 混合检索：外卖评论场景为什么要用向量 + BM25？BM25 原理是啥？

## 为什么用混合检索？

外卖评论场景有几个明显特征：

* 用户 query 很短，比如“炸鸡很脆”“送得快吗”“包装漏汤”
* 评论中有大量 **口语、错别字、同义表达**
* 又经常包含 **品牌名、菜名、专有词、数字、情绪词**

只用向量检索的问题：

* 对精确词匹配不稳定
* 对“脆”“酥”“焦香”这类可能好，但对“漏汤”“半小时”“满减”“霸王茶姬”这类词面信息不够敏感

只用 BM25 的问题：

* 只能看字面，不擅长语义泛化
* “配送快”和“半小时送到”不一定能很好匹配

所以必须 **混合检索**：

* **向量检索**：解决语义相似
* **BM25**：解决关键词精确命中
* **融合**：提升整体 Recall 和稳定性

---

## BM25 原理

BM25 是经典稀疏检索算法，本质是 TF-IDF 的改进版。它会综合：

* **TF（词频）**：词在文档中出现越多，越可能相关
* **IDF（逆文档频率）**：越稀有的词区分度越高
* **长度归一化**：避免长文天然得高分

常见公式：

```text
score(q, d) = Σ IDF(qi) * ( tf * (k1 + 1) ) / ( tf + k1 * (1 - b + b * |d| / avgdl) )
```

其中：

* `tf`：词项在文档中的词频
* `|d|`：当前文档长度
* `avgdl`：平均文档长度
* `k1`：控制词频饱和，常取 1.2 ~ 2.0
* `b`：控制长度归一化，常取 0.75

---

## 面试答法

> “外卖评论场景我会用混合检索。因为评论里既有大量口语化语义表达，也有品牌名、菜名、价格、数字、专有词这类强关键词特征。向量检索擅长语义匹配，BM25 擅长精确词项匹配，二者并行召回后再融合或 Rerank，通常比单一方案更稳。BM25 本质是基于词频、逆文档频率和文档长度归一化的打分函数，适合补齐向量检索对实体词、数字和短 query 的短板。”

## 3. 文档切割：酒店长文档（设施 + 政策 + 评价）怎么切才能不割裂语义？

## 题目本质

考的是 **chunking 策略**。
不是简单“每 500 token 切一刀”，而是要考虑业务结构。

---

## 标准思路

### 原则 1：按语义边界切，而不是机械定长切

酒店长文档明显天然分段：

* 酒店基础介绍
* 房型信息
* 设施说明
* 入住/退房政策
* 儿童/宠物/早餐规则
* 交通指南
* 评论摘要 / 原始评价

优先按这些结构切。

### 原则 2：不同类型的数据分开切

设施、政策、评价最好不要混在同一个 chunk 里。

因为：

* query 通常会很明确，比如问“停车”或“早餐时间”
* 混合在一起会降低 chunk 纯度，影响召回和重排

### 原则 3：保留父子关系

推荐：

* 子块：200~300 tokens
* 父块：一个完整段落或一个完整模块

这样可以：

* 子块负责命中
* 父块负责补足上下文

### 原则 4：相邻重叠

适当 overlap，比如 30~50 tokens，避免句子或列表被切断。

### 原则 5：保留 metadata

chunk 附带字段：

* 酒店 ID
* 文档类型（设施/政策/评论）
* 更新时间
* 来源（官方/用户评论）
* 章节标题

这对过滤和 rerank 很重要。

---

## 工程建议

### 酒店类文档适合“结构化优先 + 文本切块”

例如：

```text
chunk 1: 酒店设施 - 停车场/游泳池/健身房/接送机
chunk 2: 入住政策 - 入住时间/退房时间/押金/发票
chunk 3: 早餐政策 - 时间/价格/儿童规则
chunk 4: 交通信息 - 距离地铁/机场/火车站
chunk 5: 用户评价 - 设施相关评论
chunk 6: 用户评价 - 交通相关评论
```

---

## 追问：为什么不能把全部评论一起切？

答：

* 评论主题混杂
* 一个 chunk 里可能同时说早餐、卫生、送餐、噪音
* 会影响召回纯度和后续回答准确性

## 4. LoRA 微调：微调点餐助手时秩怎么选？A/B 矩阵初始化方式？为什么不能插在 LN 后？

这题很容易被追问到原理层。

---

## 4.1 LoRA 是什么？

LoRA（Low-Rank Adaptation）核心思想：

> 不直接更新原始大模型权重，而是在某些线性层上叠加一个低秩增量矩阵。

原始权重：

```text
W ∈ R^(d_out × d_in)
```

LoRA 训练的是：

```text
ΔW = B A
A ∈ R^(r × d_in)
B ∈ R^(d_out × r)
```

最终前向：

```text
y = W x + B A x
```

其中 `r << min(d_in, d_out)`，所以训练参数量大幅减少。

---

## 4.2 秩 r 怎么选？

### 回答原则

秩不是越大越好，而是 **表达能力和参数效率的平衡**。

### 一般经验

* 小任务、风格迁移、格式对齐：`r = 4 / 8 / 16`
* 中等复杂任务：`r = 16 / 32`
* 任务复杂、领域差异大：可更高

### 点餐助手怎么选？

点餐助手主要做：

* 意图识别
* 菜品理解
* 槽位填充
* 工具调用格式对齐

这种任务偏 **格式学习 + 业务表达适配**，通常不需要很大的 rank。
一般从 `8` 或 `16` 开始试，做 ablation：

* 看 loss
* 看下游任务指标
* 看过拟合情况
* 看吞吐和显存

### 标准面试话术

> “我一般不会拍脑袋定 rank，而是结合任务复杂度和资源预算做小范围实验。像点餐助手这类偏指令跟随和格式对齐任务，通常 rank 8 或 16 就够用；如果涉及更强的领域知识迁移或复杂生成能力，再考虑 32 以上。”

---

## 4.3 A/B 矩阵初始化方式

LoRA 里常见初始化方式：

* `A` 随机初始化（如高斯/kaiming）
* `B` 初始化为 0

为什么这样做？

因为这样在训练开始时：

```text
ΔW = BA = 0
```

也就是一开始模型行为和原模型完全一致，训练更稳定。
随着训练进行，`B` 再逐步学出有效增量。

### 一句话记忆

**A 随机，B 置零，保证初始增量为 0。**

---

## 4.4 为什么不能插在 LN 后？

这题容易答偏。

更准确的说法不是“绝对不能”，而是：

> **LoRA 通常插在线性投影层（如 Q/K/V/O、FFN 的 W1/W2）上，而不是 LayerNorm 后面，因为 LN 本身不是主要承载表达变换的参数矩阵。**

### 原理解释

LayerNorm 的作用是对激活做归一化：

```text
LN(x) = γ * (x - μ) / σ + β
```

它的参数量很小，主要做缩放和平移，不是大容量线性变换层。
而 LoRA 假设：

> 模型任务适配所需的更新可以用某个“大矩阵”的低秩增量近似。

这个假设在线性层上成立得更自然，在 LN 上意义不大。

### 进一步解释

LoRA最适合插入的地方是：

* Attention 中的 `Wq/Wk/Wv/Wo`
* MLP 中的 `W_up/W_down`

因为这些层是信息投影的主干，低秩更新可以明显改变表示空间。
LayerNorm 只管数值稳定和归一化，不是最有效的适配位置。

### 面试更稳的说法

> “LoRA 更适合加在线性投影层上，因为这些层承载了主要的表示变换；LayerNorm 主要做归一化，参数量小、表达容量低，放在那里通常收益不高，也不符合 LoRA 的低秩增量假设。”

## 5. 微调方法对比：到店评价生成场景，SFT / LoRA / QLoRA 怎么选？

## 核心思路

先看业务目标：

“到店评价生成”大概率是：

* 根据用户消费内容、标签、商户特征生成评价
* 或者客服辅助生成评价回复

这个任务本质偏：

* 风格对齐
* 指令跟随
* 领域表达适配

不是纯知识注入。

---

## 三种方法区别

### 1）SFT（全量或部分监督微调）

特点：

* 直接用标注数据训练模型输出
* 效果最好潜力最大
* 成本高、显存高、训练部署复杂

适合：

* 数据量较大
* 对效果要求高
* 有足够算力

### 2）LoRA

特点：

* 参数高效
* 部署灵活
* 适合业务微调

适合：

* 领域适配
* 风格适配
* 资源有限但追求不错效果

### 3）QLoRA

特点：

* 在 LoRA 基础上把底座模型量化到 4bit
* 显存更省
* 训练更便宜
* 可能有轻微精度损失

适合：

* 单卡或资源受限场景
* 快速实验验证

---

## 到店评价生成如何选？

### 如果数据很多、效果要求很高、算力足

优先：**SFT**

### 如果是常规业务落地，成本敏感

优先：**LoRA**

### 如果算力紧张，先做低成本试验

优先：**QLoRA**

---

## 面试话术

> “到店评价生成本质是一个领域表达和风格对齐任务。如果有较大规模高质量标注数据、且对效果极致要求高，可以做 SFT；但从成本和迭代效率考虑，业务场景里更常用 LoRA。若算力受限、需要在单卡或低资源环境快速验证，QLoRA 是更合适的选择。我的选择标准主要看数据规模、资源预算、线上效果目标和迭代速度要求。”

## 6. Function Call：调用外卖 API 的 Function Call 训练数据怎么构造？

## 核心考点

你是否理解 Function Call 不是“让模型随便输出 JSON”，而是要通过数据教会模型：

* 什么时候该调用工具
* 调哪个工具
* 参数怎么填
* 什么时候不该调

---

## 数据构造思路

### 1）定义工具集合

例如外卖场景里可能有：

* `search_shop`
* `search_dish`
* `create_order`
* `add_to_cart`
* `query_order_status`
* `cancel_order`
* `apply_invoice`

每个函数有明确 schema。

### 2）构造用户意图样本

包括：

* 明确调用类
* 含糊表达类
* 多槽位补全类
* 不应调用类

### 3）构造监督格式

训练样本应该包含：

* 用户输入
* 上下文
* 工具定义
* 目标输出（tool call or normal answer）

### 示例

```json
{
  "messages": [
    {"role": "user", "content": "帮我点一份肯德基的香辣鸡腿堡套餐，不要冰可乐"}
  ],
  "tools": [...],
  "target": {
    "tool_name": "create_order",
    "arguments": {
      "shop_name": "肯德基",
      "dish_name": "香辣鸡腿堡套餐",
      "drink_option": "可乐",
      "ice": "去冰"
    }
  }
}
```

### 4）关键样本类型一定要覆盖

#### 正样本

该调用工具，并且参数清晰

#### 缺槽样本

用户说得不完整，模型应追问而不是乱调
比如：

* “帮我点个汉堡”
* 缺商家、规格、配送地址

#### 多轮补全样本

用户第一轮给一部分参数，第二轮补充

#### 干扰样本

用户只是咨询，不该直接下单
例如：

* “肯德基最近有啥套餐？”
* 应该查商品或介绍，而不是下单

#### 负样本

不需要工具时直接自然语言回答

---

## 八股原理

Function Call 训练数据本质是训练模型做：

* **意图分类**
* **槽位抽取**
* **结构化映射**
* **工具选择决策**

所以数据不光要有“正确 JSON”，还要覆盖：

* 歧义
* 缺参
* 多轮
* 误触发
* 拒调

## 7. Agent 反思：客服答错时怎么设计反思机制让它自己纠正？

## 核心思路

反思机制不是让模型“想一想”，而是设计一个 **可控的纠错闭环**。

---

## 常见方案

### 方案一：自检（Self-Reflection）

第一次回答后，让模型再看一遍自己的回答，检查：

* 是否回答了用户核心问题
* 是否和检索证据一致
* 是否遗漏关键条件
* 是否调用错工具
* 是否存在幻觉

### 方案二：生成-验证-重写

流程：

```text
生成初稿
-> 验证器检查
-> 有问题则生成修正版
```

验证器可以是：

* 规则检查器
* 小模型 verifier
* 同模型第二次校验

### 方案三：基于错误类型做针对性反思

比如客服答错常见原因：

* 漏查知识库
* 工具调用不完整
* 状态没更新
* 多轮上下文丢失
* 答非所问

可以对不同错误设计不同反思 prompt。

---

## 一个落地的客服反思链路

```text
用户提问
-> Agent 生成回答
-> Reflection 模块检查：
   1. 是否命中用户意图
   2. 是否与知识库/工具结果矛盾
   3. 是否缺少关键信息
   4. 是否需要补充澄清
-> 若失败：
   - 重新检索 / 补查工具 / 重写回答
-> 输出最终版本
```

---

## 面试官喜欢听的点

反思不要无限循环，要有限次：

* 最多反思 1~2 轮
* 超过阈值就人工兜底或输出保守回答

否则：

* 延迟高
* 成本高
* 还可能越想越偏

## 9. MLA 注意力：对话系统如何用 MLA 减少 KV Cache 开销？能用 RoPE 吗？

> 这里的 MLA 一般指 **Multi-head Latent Attention** 一类的低秩潜变量 KV 压缩思路，核心是降低推理阶段 KV Cache 开销。

---

## 9.1 为什么 KV Cache 会成为瓶颈？

自回归生成时，每生成一个 token，都要缓存之前每层的 K/V。
长对话时：

* 上下文越长
* 层数越多
* 头数越多
* hidden size 越大

KV Cache 显存就会迅速膨胀。

所以在线对话系统里，长上下文经常是被 **KV Cache 卡住**，不是算力卡住。

---

## 9.2 MLA 的核心思想

传统 MHA 里每个 head 都存独立 K/V。
MLA 的思路是：

> 不直接存高维完整 K/V，而是先把信息压缩到更低维 latent space，再在需要时恢复或参与注意力计算。

本质是一种：

* 低秩表示
* 共享潜变量
* 压缩存储

这样能显著降低缓存体积。

### 直观理解

原来每个 token 要存很多头的 K/V，
现在只存一个更紧凑的 latent 表示，推理时再投影回来。

---

## 9.3 对话系统如何用 MLA？

在对话系统里，MLA 适合：

* 长对话客服
* 多轮助手
* 高并发在线推理

收益主要体现在：

* 降低显存占用
* 提高 batch size
* 降低单位请求成本
* 允许更长上下文

---

## 9.4 能用 RoPE 吗？

可以，但要看具体实现位置。
更准确的回答是：

> “MLA 和 RoPE 不冲突，但 RoPE 作用在 Q/K 的位置编码表示上。如果 K 做了 latent 压缩，需要保证位置编码信息在压缩和恢复过程中不被破坏，通常要在设计上兼容 RoPE 的旋转结构。”

### 原理

RoPE（Rotary Position Embedding）本质是在 Q/K 向量空间中做旋转，使相对位置信息内化到内积里。
如果你先压缩再旋转，或者旋转信息丢了，就会影响注意力的相对位置建模。

所以面试时最稳的说法：

> “理论上可以兼容，但不能简单生搬硬套，要确保 latent 表示和恢复后的 K/Q 仍然保持 RoPE 所依赖的相对位置结构。”

---

## 10. 长度外推：处理超长对话历史时，Qwen 怎么做长度外推？NTK-aware 原理？

---

## 10.1 什么是长度外推？

训练时模型只见过比如 8k 上下文，但线上想喂 32k、64k。
这就叫 **长度外推**。

问题在于：

* 位置编码超出训练分布
* 注意力模式会失真
* 长距离依赖变差

---

## 10.2 Qwen 类模型怎么做长度外推？

常见方案包括：

* **RoPE scaling**
* **NTK-aware scaling**
* 插值/缩放位置索引
* Long context continued pretraining

面试里通常重点答 **RoPE 外推 + NTK-aware**。

---

## 10.3 NTK-aware 原理

RoPE 中不同维度对应不同频率，位置越远，旋转角度变化越大。
当长度超出训练范围时，原始频率分布会导致高频部分变化过快，模型难以泛化。

NTK-aware scaling 的核心思想：

> 通过重新缩放位置索引或频率底数，让高长度区间的位置变化更平滑，从而让模型在超出训练长度时仍能保持较好的注意力结构。

可以理解为：

* 不让远距离 token 的旋转“转得太快”
* 让长上下文下的相对位置关系更接近训练时分布

### 面试可讲法

> “RoPE 的外推问题本质是高频位置分量在长上下文下变化过剧，导致注意力失真。NTK-aware scaling 会对位置映射做缩放，使超长长度下的旋转频率分布更平滑，从而改善长度外推能力。”

## 11. RL 算法选择：优化推荐助手时选 DPO / PPO / GRPO？GRPO 损失公式？

这题很容易把人问懵。

---

## 11.1 三者区别

### PPO

经典 RLHF 做法：

* 需要 reward model
* 通过策略梯度更新
* 有 KL 约束防止偏离参考模型太多

优点：

* 理论成熟
* 表达能力强

缺点：

* 训练复杂
* 采样成本高
* 不稳定

### DPO

不显式训练 reward model，直接基于偏好对做优化。
输入通常是：

* 同一 prompt
* 一个 chosen
* 一个 rejected

优点：

* 比 PPO 简单
* 稳定
* 工程落地成本低

适合：

* 有偏好对数据
* 追求训练简单

### GRPO

一般可理解为 Group Relative Policy Optimization，一类相对组内奖励优化思路。
核心是：

* 对同一 prompt 采样多个输出
* 计算组内相对优势
* 用组内比较来更新策略

优点：

* 减少对单独 reward model 标定的依赖
* 对多样输出质量排序更友好

---

## 11.2 推荐助手场景怎么选？

### 如果已有高质量偏好对数据

优先：**DPO**

### 如果已有成熟 reward 模型、资源足、追求上限

考虑：**PPO**

### 如果更关注组内比较、排序式优化，或者做 reasoning / 多候选优化

可考虑：**GRPO**

---

## 11.3 GRPO 的核心思想与损失

严格不同实现会略有差异，面试不用死抠某个论文符号，核心说清楚就行：

对同一个 prompt 采样一组响应 `y1, y2, ..., yn`，根据奖励或打分算出组内相对优势：

```text
A_i = (r_i - mean(r)) / std(r)
```

然后像 PPO 一样对策略做相对更新，但不一定依赖单独价值网络。
常见形式会有：

* 比例项 `πθ / πθ_old`
* clip 截断
* KL 正则

一个可说的抽象形式：

```text
L = E[min(ratio_i * A_i, clip(ratio_i, 1-ε, 1+ε) * A_i)] - β KL(πθ || πref)
```

其中 `A_i` 是组内标准化后的相对优势。

### 面试话术

> “GRPO 的核心不是看一个样本绝对好不好，而是看同一 prompt 下多个候选之间谁更好，通过组内相对奖励构造优势，再做策略更新。它很适合多候选比较和相对排序优化场景。”

## 12. 多轮对话设计：用户从查订单突然问发票，客服 Agent 怎么管理状态？

这题很典型，考你是否理解 **多轮状态机 + 会话上下文管理**。

---

## 核心问题

用户可能在对话中突然切换任务：

* “我的订单什么时候到？”
* “对了这个能开发票吗？”
* “发票抬头改成公司名”
* “那我刚才那个订单还能退吗？”

如果没有状态管理，Agent 很容易：

* 把发票问题和订单查询状态混掉
* 槽位污染
* 调错工具

---

## 标准设计

### 1）显式维护会话状态

不要只靠自然语言 history，要有结构化 state：

```json
{
  "current_intent": "invoice_query",
  "active_order_id": "12345",
  "slots": {
    "invoice_type": null,
    "title": null
  },
  "previous_task": "order_status_query"
}
```

### 2）支持任务切换

识别到“突然问发票”时，不是继续沿用订单查询流程，而是：

* 暂存上一任务状态
* 切入新子任务状态
* 必要时建立 task stack

### 3）槽位隔离

不同任务的槽位单独维护：

* 订单查询槽位
* 发票申请槽位
* 售后槽位

避免污染。

### 4）上下文恢复

处理完发票任务后，可以提示：

* “关于刚才那个订单，您还需要我继续帮您查询配送进度吗？”

---

## 更高级说法：用状态机 / 有限状态自动机

客服场景非常适合状态机：

* `Idle`
* `OrderQuery`
* `InvoiceQuery`
* `RefundFlow`
* `ComplaintFlow`

状态之间有明确跳转条件和工具调用权限。

### 面试高分点

> “多轮客服不能只靠模型从 history 里猜状态，生产里一定要把关键业务状态结构化管理，否则跨轮任务切换时很容易出现上下文污染和工具误触发。”

## 13. Reranker 微调：到店搜索 Reranker 的正负样本怎么标注？点击数据有偏吗？

---

## 13.1 正负样本怎么来？

Reranker 的目标是给 `(query, doc)` 打更精准相关性分数。
训练数据可来自：

### 正样本

* 用户点击的商户/团单
* 下单/收藏/到店核销
* 人工标注为相关的文档

### 负样本

* 曝光未点击
* 同 query 下排名靠前但未转化
* BM25 / 向量召回出来但人工判不相关的样本
* hard negatives：很像但不满足意图的结果

---

## 13.2 点击数据有偏吗？

**有，而且非常严重。**

常见偏差：

### 1）位置偏差

排得高更容易被点，不一定更相关。

### 2）曝光偏差

用户只会点击看到的内容，没看到的不代表不相关。

### 3）选择偏差

点击受价格、图片、品牌、活动等影响，不完全等于文本相关性。

### 4）反馈回路偏差

系统排高 -> 更容易被点 -> 用点击继续训练 -> 更加排高

---

## 13.3 怎么缓解点击偏差？

* 加入随机曝光数据
* 用 dwell time、下单、核销等更强反馈
* IPS / propensity weighting
* 人工标注补齐
* 构造 hard negative
* 将“点击相关性”和“商业转化”拆开建模

### 面试话术

> “点击数据可以做弱监督，但它有明显的位置偏差、曝光偏差和商业因素偏差，所以不能把点击直接等价为相关性标签。通常会结合随机曝光、强反馈行为和人工标注来做去偏或补标。”

---

## 14. Query 改写：外卖搜“炸鸡”想要“炸鸡 + 可乐”，怎么通过改写召回？

---

## 题目本质

考你是否理解：

* Query 理解
* 意图补全
* 召回增强
* 但不能瞎改

---

## 可行方案

### 1）基于共现和行为日志做改写

如果历史日志显示：

* 搜“炸鸡”的用户常点“炸鸡套餐”
* 高频共点项是“可乐”
  那可构造扩展 query：
* 炸鸡 套餐
* 炸鸡 可乐
* 炸鸡 双人餐
* 炸鸡 配饮料

### 2）多路召回，不是直接替换原 query

不要把“炸鸡”粗暴改成“炸鸡+可乐”，因为可能误伤原始需求。
更稳的方式是：

* 原 query 召回一路
* 扩展 query 召回一路
* 套餐意图召回一路
* 最后融合

### 3）条件触发

只有当：

* 用户历史偏好显示常点套餐
* 当前场景是推荐式搜索
* 数据强表明“炸鸡”高频伴随“可乐”
  才适合扩展

### 4）重排层控制

扩展召回不等于强行置顶，最终还是由 reranker 决定是否“炸鸡+可乐”更符合意图。

---

## 面试高分点

> “Query 改写最好做成 query expansion 或 multi-query recall，而不是粗暴改写原 query。因为‘炸鸡’未必一定想要可乐，更合理的是基于共购、用户画像和场景条件做多路扩召，再由重排阶段决定最终结果。”

## 15. 解码策略：客服回复时 Top-K / Top-P / 温度怎么设？不同业务有区别吗？

---

## 三个参数分别控制什么？

### 温度（temperature）

控制分布平滑程度。
越低越保守，越高越发散。

### Top-K

只从概率最高的 K 个 token 里采样。

### Top-P

从累计概率达到 P 的最小 token 集里采样。

---

## 客服场景如何设？

客服场景通常要求：

* 稳定
* 少幻觉
* 少跑偏
* 语气礼貌
* 不要太发散

所以一般：

* 温度偏低：`0.2 ~ 0.7`
* Top-P 中等偏低：`0.8 ~ 0.95`
* Top-K 可较小或直接不用

很多严肃客服甚至直接：

* greedy
* 或 very low temperature

---

## 不同业务的区别

### 客服 / 金融 / 医疗问答

* 低温
* 低随机性
* 更稳定

### 创作 / 文案 / 营销

* 温度更高
* Top-P 更开放
* 允许更有创意

### 工具调用 / JSON 输出

* 温度更低
* 甚至接近 0
* 减少格式错误

---

## 面试话术

> “客服回复更看重稳定和一致性，所以我会把温度设低，比如 0.2 到 0.5，Top-P 控制在 0.8 到 0.95；对于工具调用或结构化输出，还会进一步降低随机性。创意文案类业务则会更高一些。参数没有唯一最优值，要看业务容错率和风格目标。”

## 16. 推理优化：在线点餐高并发场景，如何优化推理减少首字延迟？

首字延迟 = TTFT（Time To First Token）

### 1）模型前优化

* 模型裁剪 / 蒸馏 / 小模型路由
* 更高效的 attention 实现
* KV Cache 优化

### 2）请求前处理优化

* Prompt 模板精简
* 减少无效上下文

### 3）服务层优化

* continuous batching

### 4）算子 / 推理框架优化

## 高并发点餐场景的实战答法

# 四、这套面经背后的高频八股原理

---

## 1. RAG 系统设计八股

一套完整回答模板：

```text
数据接入
-> 清洗去重
-> 分层切块
-> 稀疏+稠密索引
-> 混合召回
-> rerank
-> 上下文组装
-> 受约束生成
-> 评测与反馈闭环
```

高分点：

* 结构化知识和非结构化知识分开处理
* 动态路由，不是所有问题都走同一链路
* 允许拒答，避免幻觉

---

## 2. LoRA 八股

### 为什么有效？

因为大模型适配某个任务，所需权重更新往往位于低秩子空间，可用低秩分解近似。

### 为什么省参数？

因为原本更新 `d_out × d_in` 个参数，现在只更新：

```text
r × d_in + d_out × r
```

当 `r` 很小时差距很大。

### 为什么常插 Q/V 或 Q/K/V/O？

这些层最直接决定注意力模式和信息投影，任务适配收益明显。

---

## 3. Function Call 八股

本质是四件事：

* 工具选择
* 参数抽取
* 结构化生成
* 执行结果回注

工程上必须有：

* schema 校验
* 权限控制
* 幂等处理
* 超时和重试
* 审计日志

---

## 4. 多轮对话八股

核心不是“记住历史”，而是：

* 当前意图
* 当前任务状态
* 当前槽位
* 历史任务栈
* 可恢复上下文

生产里一定要：

* 结构化 state
* 状态机
* 槽位隔离
* 任务切换显式建模

---

## 5. 推理优化八股

可以从三个阶段说：

### Prefill

* 压缩上下文
* Prefix cache
* Prompt 模板优化
* 检索并行

### Decode

* KV cache
* 高效 attention
* speculative decoding
* 量化

### 服务化

* batching
* 异步队列
* 模型路由
* 热点缓存

# 五、这套面经中最容易被继续追问的问题

---

## 追问 1：为什么 RAG 里不能只靠评论？

答：

* 评论主观
* 信息滞后
* 噪声大
* 事实性不足
  所以评论适合做“感知补充”，不适合做唯一事实来源。

---

## 追问 2：为什么 Query 改写不能直接硬改？

答：

* 会偏离用户真实意图
* 召回召偏
* 影响精准搜索
  更合理的是多路扩召，而不是替换原 query。

---

## 追问 3：为什么客服场景温度要低？

答：

* 客服强调一致性和准确性
* 高温会增加随机性和幻觉
* 结构化输出更容易错格式

---

## 追问 4：点击数据为什么不能直接当真标签？

答：

* 点击受位置、曝光、活动、图片、价格等多因素影响
* 并不完全等于“相关性”

---

## 追问 5：LoRA 为什么常见 A 随机、B 置零？

答：

* 保证训练初始 `ΔW = 0`
* 初始行为等价于原模型
* 更稳定

# 六、面试时建议你怎么答，最容易显得“懂”

你可以把很多题统一成下面这种风格：

## 模板 1：先说目标，再说方案，再说 trade-off

例如：

> “这个问题我会先从业务目标拆解。比如酒店问答的核心是高准确和低幻觉，所以我不会只做纯文本向量检索，而是结构化信息优先、评论做补充。技术上我会做混合召回、父子 chunk 和 rerank，但同时要注意时效性和证据冲突问题。”

---

## 模板 2：不要只说“怎么做”，要说“为什么不是别的”

例如：

> “外卖搜炸鸡做改写时，我不会直接把 query 改成炸鸡加可乐，因为这会引入意图污染。更合理的是做多路扩召，把套餐类候选拉回来，再由 reranker 判断是否真的更符合用户意图。”

---

## 模板 3：所有大模型系统题，都补一句评测和闭环

例如：

> “这个方案上线后我会分别看召回指标、答案正确率、工具调用成功率和线上转化指标，并用 badcase 回流优化 query 改写和 reranker 训练集。”

---

# 七、最后给你一版“精简背诵版”

## 一面速背版

1. **酒店 RAG**：结构化知识优先，文本混合检索补充，评论做感知增强，最终答案受证据约束。
2. **混合检索**：向量抓语义，BM25 抓关键词和实体词，二者结合更稳。
3. **文档切割**：按语义模块切，设施、政策、评价分开；小块召回，大块回填。
4. **LoRA 秩**：根据任务复杂度和资源预算选，点餐助手一般 8/16 起试；A 随机、B 置零。
5. **SFT/LoRA/QLoRA**：效果优先选 SFT，工程落地常选 LoRA，资源紧张用 QLoRA。
6. **Function Call 数据**：覆盖该调、不该调、缺参、多轮补槽、歧义场景。
7. **Agent 反思**：生成后做自检或 verifier 校验，必要时重检索、重写，反思次数有限。
8. **LC25**：按组检查长度，翻转一段，连接前后。

## 二面速背版

9. **MLA**：通过 latent 压缩减少 KV Cache，适合长对话高并发；理论上可兼容 RoPE，但要保持位置结构。
10. **长度外推**：Qwen 常用 RoPE scaling / NTK-aware，让长上下文位置变化更平滑。
11. **DPO/PPO/GRPO**：偏好对数据多选 DPO；资源足、追求上限可用 PPO；多候选组内比较可用 GRPO。
12. **多轮状态管理**：结构化 state + 槽位隔离 + 任务切换 + 状态机。
13. **Reranker 微调**：点击可做弱监督，但有位置偏差、曝光偏差，要去偏和补标。
14. **Query 改写**：不要硬改原 query，做多路扩召更稳。
15. **解码策略**：客服低温低随机；创作类可更开放；工具调用温度更低。
16. **推理优化**：上下文裁剪、缓存、continuous batching、量化、模型路由，重点降 prefill 开销。
17. **LC143**：找中点、反转后半段、交替合并。

# 八、你接下来最应该准备的点

这套面经里，最值得重点准备的是这 6 个：

1. **RAG 系统设计**：能否按业务说出结构化 + 非结构化混合方案
2. **LoRA 原理**：不仅知道怎么用，还知道为什么有效
3. **Function Call / Agent**：数据怎么构造、工具怎么调、状态怎么管
4. **长上下文**：RoPE、NTK-aware、KV Cache、MLA
5. **Reranker 和 Query 改写**：这是应用岗非常高频的系统题
6. **推理优化**：TTFT、batching、KV cache、路由、缓存
